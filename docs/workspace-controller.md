# Workspace controller API

## Ownership and composition

[Workspace layout](workspace-layout.md) owns geometry and interaction requirements; [application preferences](architecture.md#application-preferences-and-bootstrap) owns durable storage. The renderer package exports `WorkspaceController`, `LayoutPreferences` and the pure geometry functions from its public entry. These controllers implement the layout boundary of [STORY-002-005](epics/EPIC-002-basic-interface/STORY-002-005-workspace-controller.md); the workspace chrome consumer supplies DOM controls, translated labels, reading positions and research buffers. PRIN-002, PRIN-006 and PRIN-013 require preserving authorship, save uncertainty and ongoing work independently of panel arrangement.

Create one `LayoutPreferences` owner per window with its admitted `FoundationPort`, a fresh operation-ID factory and an application-lifetime failure-announcement callback. Keep that owner alive when replacing a mounted controller so accepted writes and their original receipts remain reconcilable. Create a `WorkspaceController` with the owner, available CSS width, coarse-pointer flag, state observer and focus-intent consumer, then await `initialize()`. A missing or rejected record selects viewport defaults; late initialization cannot replace a persistent manual choice. All persistent layout actions are unavailable until initialization settles; the state exposes `initializing` for the consumer's controlled availability treatment. `initialize()` is single-use per controller and repeated calls share its original promise, so it cannot refresh or rearrange an existing live layout. Narrow selection and focus mode remain in memory while a late load updates their underlying wide preferences. A fresh saved layout is read when the controller is created, while subsequent saves from other windows do not rearrange it.

`state` supplies detached preference/geometry snapshots, initialization/focus-mode/drag flags, the transition policy and controlled persistence outcomes. Consumers apply panel visibility without destroying private buffers or task state. `viewport(width, coarse, focusedPanel)` handles passive reflow, including zoom; it never saves. `select(panel)` selects one narrow region. `visibility(panel, focusedPanel)`, `reset(focusedPanel)`, completed resize actions and pair reset submit complete records. `focusMode()` keeps its restoration snapshot only in memory. Actions return controlled availability and focus intents; before hiding the focused panel, the synchronous focus consumer moves focus to its panel control. Pass the actual focused region to narrow Reset; omit it when a Settings/dialog control owns focus. When an initial loaded snapshot hides a focused provisional region, the consumer moves focus to its always-present panel control before applying that snapshot to the DOM.

## Resizing

Use `separatorRange` for the left panel's accessible minimum/current/maximum and the geometry's ordered `pairs` for actual neighbors. `key(left, right, key, shift)` handles arrows, Home, End and Enter. `size(panel, increase)` is the non-drag button alternative. `pairReset(left, right)` is the double-click action; Enter uses that same calculation. One visible region exposes no pairs or sizing action.

`beginResize` takes the initiating pointer ID, its CSS x coordinate and a `ResizeHost` that captures/releases that pointer and locks/unlocks cursor and selection. Forward matching movement to `moveResize` and pointer release to `endResize`. Forward Esc, pointer cancellation and focus loss to `cancelResize` with their typed reasons. Viewport/visibility changes and `dispose()` also cancel and restore the starting geometry. Consumers disable CSS width transitions while `state.transitions` is false. No pointer movement writes a preference. A zero-movement or clamped resize returns `unchanged` without saving effective viewport clipping; the explicit pair-reset command commits its intentional reset once, including after the two no-movement pointer releases of a double-click.

## Persistence and recovery

The existing named port exposes `readLayout`, `replaceLayout` and `readLayoutReceipt`; callers receive no arbitrary key or storage access. The exact version-1 value lives in [the contracts module](../packages/contracts/src/layout.ts). Read envelopes contain schema version, revision, source and value; missing/invalid values carry `null`, allowing defaults to use the actual viewport. Invalid stored bytes are preserved until an explicit replacement. A failed layout read alone does not revoke research-storage admission.

The utility serializes complete records and atomically commits the `workspace_layout` preference and its `layout_receipts` row. Migration `0004_layout_receipts` uses the existing immutable migration registry, checkpoint and compatibility path. A repeated operation with identical content returns its original result; changed content with that identity conflicts. A stale expected revision yields a recorded conflict. Each later explicit action has a fresh identity; no stale record is retried automatically. Successful resizing saves visible effective widths and preserves hidden preferred widths; visibility-only writes preserve every preferred width.

After an actually failed initial load, defaults are this window's live preferred record. A later explicit action writes that complete record; revision recovery does not replace its preferred widths or merge another window's saved layout into it. In particular, a visibility-only action preserves this window's fallback widths even if revision admission discovers a different saved record. A new explicit complete-record save with no known revision first shares or starts a bounded preference read; a later explicit action can recover after an initial read failure without rearranging the live layout or retrying an old mutation. An unresolved write makes further persistent layout actions unavailable while passive reflow, narrow selection and focus-mode changes remain usable. `LayoutPreferences.reconcile()` queries the exact pending identity. Pending/absent receipts retain uncertainty; a recorded outcome resolves it. `load()` refreshes the authoritative revision and reports read failures separately from saved success. Refreshes coalesce only within the same confirmed-write epoch and submitted-attempt barrier; `load(true)` starts a fresh initial read for a new controller. A read requested during a submitted write waits for that attempt to settle, while an admission read never waits on its own future write. Superseded readers receive the latest read outcome, including an already settled one, without publishing obsolete state. The owner retains one monotonic authorized `readModel` from successful reads and matching committed receipts; initialization consults it before applying a successful result. A legitimately overtaken read can yield a newer confirmed model. If a conflict advances only the known revision, the reader makes at most one fresh recovery read; another conflict during that recovery returns the actual `stale_revision` outcome. A genuinely regressed current response remains an inspectable read error; it never repeats a mutation or rearranges a live controller. Controller disposal detaches its observer while the window-owned preference session retains accepted writes. The broker's named `claimLayoutFailureNotice` operation grants at most one failure announcement per application lifetime across windows and service replacements; definitive save failures remain inspectable in each window's state. Uncertainty remains separate and does not claim the failure announcement.

## Verification boundary

[The deterministic harness](../tests/workspace-layout.test.ts) exercises allocation oracles, all visibility combinations, fractional widths, resizing alternatives, cancellation, focus/narrow behavior and late-response schedules. [Storage tests](../tests/storage.test.ts) exercise real file-backed transactions, conflicts, failure, restart and unrelated preference preservation under the pinned developer-Node addon. [Port tests](../tests/port.test.ts), [preload composition tests](../tests/preload-entry.test.ts) and [broker composition tests](../tests/main-entry.test.ts) exercise schemas, identity, cancellation and the shared failure-notice claim. The [shared verification aggregate](shared-verification.md) accounts for these tests and coverage. These boundaries do not establish packaged chrome, manual assistive operation or native Electron qualification; those checks belong to their consumer and native verification workflows.
