# Shared desktop delivery admission

[The artifact-to-cell contract](epics/EPIC-001-desktop-foundation/epic.md#spec-001-028-linux-first-delivery-and-platform-capability-admission), [ADR-0021](adr/adr-0021-versioned-desktop-artifacts.md) and [ADR-0038](adr/adr-0038-desktop-delivery-mechanisms.md) govern package identity and native coverage. [The shared reconciler](../scripts/delivery_admission.py) provides schema version 1 for candidate, publication and integrated-acceptance consumers. Its result concerns a specific immutable metadata bundle; it performs no build, signature, provider request, installation or publication.

## Trust boundary and invocation

A trusted consumer supplies `Context` independently of the producer's metadata. It pins the expected subject and complete capability manifest by canonical SHA-256, the selected targets, operation, trusted current time, revoked evidence hashes and independently admitted baseline inventory hashes. The manifest pin must come from the consumer's authenticated selection or retained registry after reconciling complete attempt history; copying a producer-supplied hash does not establish authority. Failed attempts may be retained outside a bounded admission bundle, but omission must be an explicit authenticated selection rather than silent truncation.

`Context.verify_evidence(record, canonical_bytes)` receives a detached parsed copy; adapter annotations or normalization cannot change the indexed receipt. It must return the Boolean `True` only after independently verifying that record's kind-specific assertions, complete execution identity, source, final artifacts and authoritative evidence. For example, provenance requires actual verified GitHub attestations for the final bytes; RPM/catalog evidence requires the permitted signer and independently obtained trust root; native results require the actual observed account, architecture, sandbox, filesystem, display and scenarios. A workflow name, checksum, successful job or producer's `outcome` alone is insufficient. When signing transforms bytes, the adapter must authenticate the transformation and final-byte provenance. A callback that merely accepts hashes from the same untrusted bundle defeats this boundary.

Baseline inventory hashes supplied through `baseline_inventories` identify complete, independently admitted previous inventories. The separate trusted `baseline_requirements` tuple maps every required cell ID to its required supported baseline inventory hashes, including empty tuples for deferred update scope; it must come from the consumer's reviewed support/retention policy rather than producer-selected coverage. Every applicable required baseline must be assigned and exercised; an authority allowlist alone cannot reduce that policy. Complete previous inventories may retain declared targets outside the current selection. The consumer rechecks their authority, compatibility and revocation at use; an arbitrary older package is not an authenticated upgrade baseline. This module does not implement signing, attestation, native-result or baseline-registry adapters. Those adapters must satisfy this contract before operational admission can be claimed.

Call `load_bundle(directory)` to read bounded canonical documents and evidence records, then `reconcile(*documents, context, records=records)`. Success returns an immutable in-process `Admitted` object; `report()` returns a detached JSON-compatible report. `AdmissionError` carries a stable refusal code. Missing or invalid required evidence refuses the whole requested operation. An absent verifier always refuses admission. The diagnostic command below deliberately has no option to import a verifier or trust producer assertions, so even a structurally correct bundle exits with refusal until a trusted consumer uses the library API:

```bash
python3 scripts/delivery_admission.py /path/to/bundle \
  --subject-sha256 EXPECTED_SUBJECT_SHA256 --now-ms TRUSTED_CURRENT_TIME_MS
```

The CLI emits only `delivery_admission_refused` on rejection. The library exposes specific codes such as `input_binding`, `artifact_bytes`, `session_package_substitution`, `scenario_coverage`, `native_environment` and `capability_unqualified`, without including raw metadata or filesystem paths. Callers treat every refusal as ineligibility and retain the evidence separately; they must not continue with a reduced required matrix.

## Canonical representation and bounds

Each document is strict UTF-8 JSON with recursively sorted object keys, compact separators and one trailing LF. Arrays retain semantic order. Duplicate keys, floating-point/nonfinite numbers, unsupported fields and noncanonical bytes are refused. Identifiers use lowercase ASCII letters, digits and hyphens; digests use lowercase hexadecimal SHA-256. Source and workflow revisions use full 40-character Git commit/tree identities. Positive numeric identity and length fields reject Boolean coercion. Every content hash covers the exact canonical bytes including LF.

The [numeric resource policy](../config/desktop/resource-policy.json) owns document, record, combined-byte and count limits. Inventory/index documents and evidence records have separate byte budgets; a valid evidence record may exceed the document budget. The combined budget includes all four documents and all indexed records. Installer bytes use the separate existing package budget and are streamed. Over-limit input is refused without truncation or silently dropping evidence. Local readers use fixed document names and digest-derived record filenames; they do not follow leaf symlinks, open nonregular files or fetch metadata URLs. Parent-directory selection and access control belong to the trusted consumer.

The [target manifest](../config/desktop/targets.json) and [capability policy](../config/desktop/delivery-capabilities.json) are trusted checkout inputs. `target_policy` hashes the parsed target manifest's canonical representation. `capability_policy` hashes the canonical object containing `targets`, `capabilities` and effective `limits`; it therefore binds target scope, scenarios, formats, signing rules and admission/package bounds. These are canonical semantic hashes, not hashes of the formatted repository JSON files.

## Four documents and evidence records

Each document has exactly `schema_version: 1` and a `subject`, plus its fields listed below. A subject contains exactly `kind`, `id`, `repository`, `application_version`, `source_commit` and `source_tree`. The kind is `quality`, `qualification` or `candidate`; the repository is `ohtia/ohtia`. Version syntax follows the existing desktop version grammar: a final version, `-beta.sequence`, or `-dev.run.attempt`. Quality and controlled qualification subjects use development versions bound to their actual build run/attempt; candidate subjects use reserved beta or final versions. Quality subjects cannot establish delivery admission. Public capability admission accepts only candidate-class, non-development baselines. All four top-level subjects must agree exactly; older baselines have their own subjects inside the artifact inventory.

### Capability manifest

`capabilities.json` adds `inputs` and `targets`. The inputs are `target_policy`, `capability_policy`, `artifact_inventory`, `cell_inventory` and `evidence_inventory`, each a canonical content hash. The last three bind the other documents, including every selected attempt through the evidence index.

Every declared target appears exactly once, including optional targets that are not selected. Each target entry contains `target` and `profiles`; each profile contains `profile`, ordered `formats` and all seven named `capabilities`: `build`, `provenance`, `native_runtime`, `catalog_authentication`, `native_package_signing`, `first_installation` and `installed_update`. Each claim has `state` and an `evidence` array of record content hashes. States are `unknown`, `unavailable`, `failed`, `passed`, `expired`, `revoked` and `not_required`. Passed claims require matching, verified, fresh, nonrevoked successful evidence with complete coverage. Historical failures stay in the index rather than contributing to a passed claim.

Only DEB native package signing may be `not_required` under the capability policy. This never waives authenticated catalogs, provenance or native installation. Unselected targets retain explicit unknown/unavailable states and no claimed success. The report records effective capability states, requested scope and per-profile `distribution_eligible` for this capability gate. Eligibility is true only after a requested public-mode reconciliation passes; other operations establish no public eligibility. Product-readiness and publication-authority gates remain with their consumers. The report always sets `publication_authorized: false`.

### Versioned artifact inventory

`artifacts.json` adds `inventories`. Each entry has `subject` and `artifacts`; its assignment reference identity is the canonical subject hash, with no repeated subject identity. The out-of-band `baseline_inventories` and `baseline_requirements` instead hash the complete canonical `{subject, artifacts}` entry, including every artifact; these authority hashes are distinct from assignment subject hashes. Each artifact contains exactly these fields:

- `id`, `targets`, `profile`, `format`, `architecture` and sorted native `slices`.
- Final original installer `sha256`, positive `bytes` and `native_version` after every byte-changing transformation.
- Stable evidence IDs `build`, `provenance` and `signing` for the corresponding receipts. These are identifiers rather than record content hashes, avoiding a hash cycle between inventory and evidence; record content integrity comes from the evidence index and pinned manifest.

An artifact reference contains exactly `inventory`, `artifact`, `sha256` and `bytes`. Its inventory identity, ID, final digest and length must resolve together. Distinct artifact identities cannot alias a digest across formats, profiles, CPUs or versions; a universal package remains one explicit multi-target record. Every current build/provenance/signing ID resolves to the matching receipt, and a passed native-signing claim covers every listed signing step. References retain declared signing lineage and do not by themselves assert currently admitted publisher trust. A previously linked receipt may become unknown, unavailable, expired or revoked without being erased from an immutable inventory; common-mode readiness remains independent, and public eligibility refuses that state. Artifacts with no performed signing attempt list no hypothetical future receipts, and the selected DEB native-signing waiver requires an empty signing list; a matching version or filename cannot substitute another package. Linux Ubuntu, Debian and Fedora profiles remain distinct. macOS retains DMG and ZIP roles. Universal macOS artifacts explicitly include both architecture targets/slices and require both targets' native cells; shared artifact-level receipts do not replace independent execution on each CPU.

### Native cell assignments

`cells.json` adds `cells`. Every cell has exactly `id`, `target`, `profile`, `os_profile`, `os_version`, `filesystem`, `security`, `display`, `scenarios` and `assignments`. Required cells are derived from trusted target policy, never from the producer's list: ten Linux cells, Windows 11 x64 and macOS 26/27 ARM64, plus the full admitted scope of any selected optional target. Environment strings are normalized policy identities; the evidence adapter verifies their concrete native observations, including supported OS floor and security enforcement.

Assignments contain `install`, `update` and `baselines`. Current roles reference the current inventory and the profile's exact format. Every baseline references an independently admitted, strictly older version of the same target/profile. Its artifact is the package that actually established the prior installation: either the profile's installation or update format, including an old DMG before a new ZIP update. Required baseline inventory coverage must exactly match the trusted per-cell support scope. Linux and full public readiness require nonempty baselines; deferred Windows/macOS update qualification does not block common foundation readiness. Every current artifact must have an assignment. Single-format profiles use the same reference for current install and update roles. X11 and Wayland cells for the same OS/profile/CPU must agree on both current roles. Reuse on another supported OS version is explicit through its separate assignment and evidence.

### Evidence index and records

`evidence.json` adds `records`, an ordered list of unique record content hashes. Each record's canonical bytes are stored in `records/<sha256>.json` or supplied through the library's `records` mapping. The index and mapping must agree exactly, and each file must match its content hash. Evidence IDs are unique across retained attempts. Indexed records belong to the current subject; older baseline receipts remain under their own independently verified inventory authority.

Each record contains exactly `id`, `kind`, `subject`, `target`, `profile`, `artifacts`, `cell`, `scenarios`, `execution`, `observed`, `outcome`, `observed_at_ms`, `expires_at_ms`, `proof_sha256` and `details`. Kinds are the seven capabilities. Outcomes are `passed`, `failed`, `cancelled`, `skipped` and `unknown`. Evidence is admissible only at `observed_at_ms <= trusted_now < expires_at_ms`, with no revocation. An execution separately records `workflow`, `workflow_sha`, positive `run_id`, `attempt`, actual GitHub `job_id` and an ASCII `invocation` identifier for the worker execution. Job IDs must agree with their workflow/run/attempt parent. Native cells use distinct consumer jobs, disjoint from all indexed build and native-signing producer jobs, including failed and unclaimed producer receipts, while build and native jobs may share one workflow run. Each retry uses a new invocation or actual job execution; an unchanged cell/scenario/artifact execution cannot have contradictory outcomes. Development build receipts must match the version's actual run and attempt. Build identity is never inferred from a later test run. A trusted verifier must reject a valid-looking receipt from the wrong run, attempt or workflow revision.

`proof_sha256` binds the retained authoritative proof bytes, independently retrieved and verified by the evidence adapter; it is not a producer success flag. The adapter verifies the raw build/signing transformation chain, attestations or native observations behind the normalized record and applies appropriate raw-proof size and transport limits. The common loader reads only bounded normalized records and never retrieves a proof URL.

Artifact-level receipts have `cell: null`, empty `scenarios` and `observed: null`. Build details contain `inputs_sha256` and `payload_sha256`; the external adapter verifies the complete build-input closure and expected installed payload comparison. Provenance details identify `github-artifact-attestation`. Native-package-signing receipts identify producer signing/final-verification executions; native consumers report their own signature checks within installation/runtime proofs, without claiming to be signing producers. Signing/catalog details contain `mechanism`, `authority` and `signer`, with independently verified authority/signer SHA-256 identities. Mechanisms distinguish `ed25519` catalogs, `openpgp-rpm`, `authenticode` and `developer-id`; the latter adapters must verify their complete platform-specific obligations.

Native evidence identifies its exact cell, scenario and ordered consumed artifacts. Update and recovery scenarios bind each baseline/update pair. `observed` matches the cell's normalized environment plus `native: true`, `ordinary_user: true`, `graphical_session: true`, `architecture`, `process_architecture` and `addon_architecture`. Every indexed native record has a declared matching cell and capability-specific scenarios. Every passed record has the exact assigned artifact combination and complete native observations, even if coverage does not select it. Failed records may retain partial or absent observations without contributing to success. A different CPU, emulated process/addon, display, account, filesystem or security observation cannot fill coverage. Native-runtime details contain `installed_payloads`, mapping each consumed artifact ID to the separately admitted build payload hash; this comparison is distinct from the original installer digest. Other scenario details are bounded structured adapter evidence and remain subject to independent verification.

## Consumption, retries and compatibility

`linux_qualification` requires all seven capabilities for Linux and build/provenance/native-runtime capability for the required macOS/Windows foundation cells. Missing publisher capabilities on those platforms remain explicit. `candidate` uses that common readiness gate with a candidate subject. `public` refuses internal `-dev` versions and requires a candidate subject and all seven capabilities for every selected required product platform and included optional target. A Linux-only target selection cannot authorize a public product. These gates do not provide the version-reservation registry, publication authorization or integrated product acceptance owned by their consumers.

`verify_payload(path, expected_artifact)` streams the actual transferred file and compares its length and SHA-256 before installation. The caller must preserve that verified file identity through use and refuse rebuild/repack/re-sign operations. `verify_uploads(admitted, receipts)` compares a complete list of `{artifact, sha256, bytes}` upload observations with the immutable in-process public admission inventory; a JSON report cannot be deserialized into authority. The consumer authenticates actual destination observations, performs fresh reconciliation at activation and controls publication. These helpers neither perform uploads nor authorize them.

A retry may use the same sealed packages with a new explicit invocation or genuine job identity, retaining failed attempts and binding the newly selected complete evidence index. It may not replace package bytes or turn stale/failing attempts into success. Changed installer bytes, embedded version, signatures or signing transformations require a new version and candidate under the existing release policy. Changed cell assignments, required policy, evidence, expiry or revocation require fresh reconciliation and invalidate the prior report's applicability. Schema field/semantic changes require an explicit versioned compatibility decision; unknown fields and producer-defined waivers are refused rather than guessed.

## Reusable consumer fixtures

[The fixture factory](../scripts/tests/delivery_fixture.py) creates complete, explicitly synthetic bundles and an out-of-band synthetic verification context. [The contract tests](../scripts/tests/test_delivery_admission.py) exercise common and public-shaped readiness, Ubuntu X11/Wayland package reuse, independent ARM64 execution, optional/universal cells, DMG/ZIP roles, baselines, authority failures, expiry/revocation, substitution, bounded readers and upload comparison. Consumers may reuse these local fixtures on their actual base without treating them as real qualification or real publisher verification.

```bash
PYTHONPATH=scripts:scripts/tests .venv/bin/python -m unittest test_delivery_admission -v
```

Synthetic authority exists only in the test helper. Native installation/update execution, operational trust adapters and full product readiness require their own actual evidence; fixture admission does not supply those guarantees.
