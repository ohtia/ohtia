# ADR-0051 — Research-agent task execution

Supersedes [ADR-0011 — Persisted local task intent with bounded execution](adr-0011-bounded-durable-local-tasks.md). This record owns the complete task/attempt execution contract; [ADR-0052](adr-0052-current-provider-dispatch-authorization.md) owns provider-transfer authorization and [ADR-0053](adr-0053-researcher-approved-specialist-collaboration.md) owns specialist coordination.

## Context

Source analysis and document processing can outlive an interface interaction, encounter a crash or lose contact with an external provider. Repeating a request after losing its response can duplicate work and cost. An in-memory-only queue loses intent and reconciliation evidence on restart. Platform schedulers can launch processes but would still require Ohtia to preserve input scope, domain receipts, cancellation authority and provider uncertainty; separate OS job definitions would also duplicate lifecycle policy. Persisted intent with one local broker keeps those decisions inside the same transaction and authority boundary as the research operation. Ohtia therefore needs persistent work intent and explicit completion evidence; a process exit, timeout or closed window alone cannot establish a research outcome.

Ohtia is a desktop application that the researcher closes and reopens. The provider routes selected for [research agents](../epics/EPIC-003-research-agents/epic.md#spec-003-010-durable-ai-tasks) are used without background execution or a cancellation endpoint. Closing a stream prevents further delivery on it while remote work and billing can remain unknown. Persisted acceptance, bounded parallel replies and distinct orderly-exit/crash recovery preserve researcher authorship (PRIN-002), provenance (PRIN-004), uncertainty (PRIN-006) and honest stopping points (PRIN-016). Requiring another researcher request after every proven unsent attempt would repeat already granted authorization; repeating a possibly dispatched attempt could duplicate work and cost.

## Decision

### Task identity and accepted work

A **task** is one accepted request for an operation on an immutable input manifest under a versioned policy. An **attempt** is one execution of that task. Only one attempt of a task can hold execution authority at a time. The task retains its ID across allowed automatic attempts; a human request to repeat terminal or unresolved work creates a new task linked to the earlier one.

Persist the task, command receipt and domain changes that schedule it in one SQLite transaction. A repeated command ID with the same payload returns the prior receipt/task; a different payload with that ID fails. Creating a task does not start a process or contact a provider before commit. A rejected admission creates no accepted task.

Retain task ID, operation, policy and instruction versions, project and conversation scope, immutable accepted input identities, the project document language at acceptance (empty during setup), command identity, state and blocking reasons, cancellation intent, current attempt/generation and cumulative retry consumption. Each attempt records its task, generation, admission, process identity, dispatch evidence, timing/limits, scoped capability, progress, outcome and terminal receipts. [ADR-0012](adr-0012-attempt-bound-process-capabilities.md) owns the capability; research results and task state commit through the trusted data service.

### Task states and transitions

Task states have the following meanings:

- `queued`: accepted and eligible for admission, waiting for capacity; no execution authority is held.
- `blocked`: accepted but not eligible to start. Persist one of these blocking codes: `connection_disabled`, `permission_required`, `input_changed`, `configuration_unavailable`, `restart_paused` or `usage_limit_reached`. Waiting for capacity alone is not a block.
- `running`: one attempt owns the reserved capacity and is preparing, executing or waiting for a scoped human answer.
- `cancelling`: cancellation has won the state transition; new research effects are denied while termination is requested and checked.
- `uncertain`: dispatch, result delivery or cessation cannot be established. Research-effect authority is revoked; unresolved work is not presumed stopped.
- `completed`: a valid result and completion receipt were accepted and committed for the current attempt.
- `failed`: execution ended without an accepted successful result, with a controlled reason and no retry remaining/allowed.
- `cancelled`: cancellation was requested and no execution began, or the required local/provider cessation evidence is confirmed.

`completed`, `failed` and `cancelled` are terminal task states; those task records never change. An `uncertain` task has revoked research authority and may reconcile to `failed` or `cancelled` only on the scoped evidence below. Completed, failed, cancelled and uncertain attempt outcomes are immutable apart from accepted token reports. Retry never reopens a terminal task or a final attempt; fresh researcher-authorized work receives a new linked task.

Allowed transitions are:

1. Acceptance creates `queued`, or `blocked` when a declared prerequisite prevents start. Clearing a block revalidates the original authorization, current restrictions, input versions and policy before `blocked → queued`; it does not silently select new inputs, another provider or a larger budget. Changed input needs a new explicitly accepted request, except for the accepted-result coalescing rule below. A connection disconnection or usage pause also allows `queued → blocked`. A usage pause sets `usage_limit_reached`; only the researcher's “Resume {service} requests” clears that pause after revalidation.
2. Admission performs `queued → running`, creates the next `prepared` attempt and reserves its capacity in one transaction. Cancellation while still `queued` or `blocked` goes directly to `cancelled`, without spawning anything.
3. Valid finalization performs `running → completed`. A proven ended failure becomes `failed`, or returns to `queued` for an allowed automatic attempt within the same cumulative budget. A prerequisite that disappeared before dispatch produces `blocked` with its reason.
4. Cancellation of `running` produces `cancelling`. Unknown dispatch/result or unproven cessation produces `uncertain`, not an assumed failure/cancellation. `cancelling → cancelled` requires the cessation evidence below; lack of that evidence produces `uncertain`.
5. Reconciliation of an `uncertain` task accepts only scoped evidence and never restores the old attempt’s research-effect authority or rewrites its final outcome. A result, task outcome and completion receipt already committed together are read back as `completed`; that is receipt recovery, not an `uncertain → completed` transition. Proven termination without a recoverable accepted result permits the task to become `failed`, or `cancelled` when cancellation was requested; otherwise it remains `uncertain`. The final attempt remains unchanged apart from accepted token reports. Another execution requires a new accepted task.

Completion and cancellation race through the same expected-version transition. If completion commits first, a later Cancel returns that terminal receipt. If cancellation commits first, a late result cannot publish research effects. Previously committed partial observations retain their actual input/coverage; cancellation does not erase them or turn them into a complete result.

The conversation reply queue permits at most one running or cancelling reply task and one not-started reply task. Enforce these constraints in the database. A new researcher message coalesces only a not-started reply task, cancelling it and creating a replacement in the same acceptance transaction, with `replaces_task_id` pointing to the old task.

On the first transition to `running`, reserve `reply_position` immediately after the highest used or reserved position in the conversation. Keep it across attempts. Later researcher messages receive later positions. Save complete or partial reply text as an agent message with `task_id` at that reservation in the finalization transaction; an outcome without text leaves the reservation unused.

When an ordinary reply, a consultation result or the result of a plan contribution is saved while a not-started reply task waits in the same conversation, atomically cancel and replace that reply task so its input includes the message. Always retain the waiting reply’s `accepted_by_operation_id` and record its ID in `replaces_task_id`. An ordinary reply saved at its reserved position retains the waiting task’s `input_through_position`. A consultation result or the result of a plan contribution can be saved after that cutoff: its replacement uses the higher of the previous cutoff and the result’s position. The added input is the result of researcher-approved work, so this replacement needs no new researcher command. A synthesis message does not replace a waiting reply or raise its input cutoff: it is the coordinator’s own assistant-role message and must not become the last item of a request. An already running reply never receives newly saved input.

[Consultation tasks](../epics/EPIC-003-research-agents/epic.md#spec-003-027-consultation) share the conversation’s execution queue with replies: together they permit at most one running or cancelling task, plus one not-started reply and one unfinished consultation. A consultation is never coalesced with messages or saved replies. [Plan contribution tasks](../epics/EPIC-003-research-agents/epic.md#spec-003-028-contribution-graphs) and synthesis tasks are outside that conversation queue and can run alongside it, subject to application, connection and operation budgets. A returning consultation, contribution or synthesis task retains its place rather than being cancelled because a reply waits. Each owning operation must establish these task-kind distinctions and database constraints before enabling the kind; STORY-003-005 itself admits only reply tasks.

Each task starts with `state_revision` 1. Every transaction changing it advances that revision once; every transaction affecting tasks or messages in a conversation advances that conversation's `revision` once, including reply saving and coalescing.

### Attempt lifecycle and completion evidence

An attempt progresses from `prepared` to `running`, optionally `waiting_user`, and then `completed`, `failed`, `cancelled` or `uncertain`. Cancellation/deadline handling uses `stopping` while termination is requested. The task stays `running` while its attempt waits for a scoped tool approval; that wait retains capacity and counts against its deadline. A human answer cannot revive a revoked, expired or replaced attempt.

The supervisor records launch intent before spawning and the OS process identity/receipt afterward. A `prepared` record without a launch receipt is not proof that a process never started: a crash can occur between spawn and receipt persistence. PID alone is insufficient; bind it to the process start identity and the application's supervised process group/job/container or equivalent verified containment identity. Reused PIDs and unrelated provider/OS processes must not be signalled.

A result is complete only when the current attempt returns a valid terminal operation result, its manifest/structure passes validation and the data service commits the result with its outcome receipt. A zero process exit or end of stream without that receipt is not success. Once research authority is revoked, only bounded exit/reconciliation/usage receipts remain admissible; do not restore write authority merely because an old child was found alive.

For local execution cessation, obtain the supervisor's exit/wait receipt and verify no owned descendants remain executing, or obtain a conclusive OS containment-termination receipt. Zombies are not executing children but must be reaped. If the identity/containment cannot be verified, cessation remains unproven. For an external turn, bind the adapter's terminal result, cancellation or inspection to that exact provider operation. For an adapter without background execution or a cancellation endpoint, closing its connection proves nothing more can arrive on that connection: a stopped attempt becomes `cancelled`, an exceeded limit becomes `failed`, and a lost connection becomes `uncertain` without retaining its slot. Remote work and usage remain unknown. Other adapters require their declared terminal/cancellation/inspection evidence before releasing unresolved capacity. Local process death alone never proves external generation or billing stopped.

### Scheduling and required limits

Persist two independent application-wide concurrency limits as preferences. `max_concurrent_inference` defaults to **10** and accepts whole numbers from 1 to 50; it is the only concurrency control in Settings. `max_concurrent_local_processing` stays stored at **1**, without a Settings control, until a feature uses local processing. The classes may overlap. Direct UI/database commands and progress/event delivery consume neither class of long-work slots, so reading and saving remain available. Advance an untouched seeded inference record from 1 to 10 with its revision; preserve an existing saved choice.

The broker enforces the saved limits when reserving capacity. A settings update and admission must be serialized so a concurrent claim cannot use a superseded limit. Lowering a limit does not cancel or interrupt admitted work: start no further attempts in that class until its occupied slots fall below the new limit. Raising a limit permits eligible queued work to start through the normal admission checks; it does not resume paused tasks, clear uncertainty or grant provider permission. Persisted quarantines count toward occupied capacity after restart and after a settings change.

A connection remains limited to one inference attempt unless its adapter explicitly declares and verifies a higher concurrency limit. Admission must satisfy both the application limit and the connection's supported limit; changing Settings cannot override adapter safety constraints, operation budgets or provider permissions.

Within each class, eligible tasks use committed `created_at` order, with `id` as the stable tie-break. Skip blocked tasks; do not silently reorder priorities or increase the configured concurrency. Reserve/release slots transactionally with their attempt transitions. Preparation, execution, waiting for human input and stopping all hold their slot. For adapters requiring separate cessation evidence, an uncertain attempt quarantines its slot until scoped reconciliation or the explicit unresolved-work procedure below. Adapters without background execution or a cancellation endpoint release it when the connection closes, as defined above. Lease expiry alone never frees unresolved capacity.

Every enabled operation policy supplies these explicit fields:

- `max_pending_tasks`: positive integer cap on this operation's queued plus blocked tasks; an active/quarantined attempt uses its execution slot instead.
- `max_input_bytes`, `max_input_items`, `max_output_bytes` and `max_work_units`: positive integer limits, with the operation defining how work units are counted.
- `max_attempt_duration_ms`, `max_inactivity_ms` and `stop_grace_ms`: positive finite integer durations. `max_inactivity_ms` is the longest interval without any provider event before an attempt stops. The attempt deadline includes human-approval waits and elapsed suspension time; inability to establish elapsed time requires reconciliation, never an extended deadline by assumption.
- `max_attempts`: 1 or 2 allocated attempts for this accepted task, counted cumulatively from preparation, including interrupted/spawn-failed attempts. A continuation cannot reset the count; exhaustion requires a new explicitly accepted task.
- `max_auto_retries`: 0 or 1, further bounded by remaining attempts/work budget.
- `retry_backoff_ms`: nonnegative finite integer delay before an otherwise admissible automatic retry.

A producer with a missing/invalid required field is unavailable. Reject a request that would exceed its admission cap before accepting the task; never silently drop older work. A batch declares a finite input list and total work budget before acceptance. Values specific to extraction, analysis or export belong in their operation contracts, not guessed universal limits here.

Permit at most **one automatic retry** per task, with a policy allowed to require zero. The budget includes all layers and survives restart; SDK, adapter and scheduler cannot each add retries. Automatic retry requires proven local cessation, no accepted prior result/effect and either conclusive zero external dispatch or the provider's verified idempotency/reconciliation contract for the same operation. Headers or body state alone must not be interpreted as proof of zero request transmission. Partial output or uncertain dispatch is not automatically retried.

For the provider-backed operations of [EPIC-003](../epics/EPIC-003-research-agents/epic.md#spec-003-004-operation-policies), `max_auto_retries` is 0: nothing dispatched is repeated automatically. A proven unsent attempt may use one complete readmission within `max_attempts`, outside `max_auto_retries`, after an orderly stop, an expired dispatch permit or a rejected renewal. Record the unsent attempt `cancelled`; requeue after an orderly stop without migration recovery with `service_restarted` or after permit refusal with `permit_expired`, and block after rejected renewal until reconnection. Keep the task's original queue order and reply reservation. If the returning task is a reply and a not-started reply already exists in its conversation, cancel the returning reply instead, silently leaving its reservation unused. Other task kinds retain their place under their operation contract. Exhausted attempts fail the task rather than resetting its budget. After a crash, the continuation rule below applies.

A deadline or inactivity limit requests interruption, then waits the operation's declared stop-grace interval for receipts. The supervised runtime must provide tested bounded termination/escalation for that platform; sending a signal is not the receipt. Expiry without the applicable local or adapter cessation evidence becomes `uncertain`, with no automatic retry or assumed slot release. The closed-connection rule above is the cessation evidence for adapters without background execution or a cancellation endpoint.

### Durable receipts and immutable input manifests

Keep transition evidence in the accepted command's `command_receipts` row, immutable task inputs and identities, `input_through_position`, `accepted_by_operation_id`, `replaces_task_id`, attempt rows and task `state_revision`. Keep no separate log of every state change. After an attempt reaches `completed`, `failed`, `cancelled` or `uncertain`, its state, outcome reason, requested and observed models, dispatch timestamp, transfer manifest, provider request identity and start/finish times never change. Only its token fields may reflect the latest accepted usage report; individual usage reports retain their own immutable identity under [ADR-0029](adr-0029-operation-profiles-and-usage-reports.md). A new execution creates a new attempt row.

A task's accepted input identities and operation policy are fixed. Build each attempt's actual input from those records and record its immutable `transfer_manifest`, including selected messages and instruction versions by reference, never by copying their contents. Build Ohtia's notes about omitted messages, proposals, plans and memory from the records as they are when that attempt's input is built. Record each note's kind and the identifier and revision of the record it describes. A later attempt builds its notes again and records its own manifest; no dispatched manifest changes.

For requests controlled by main, the permit transaction writes `dispatch_permitted_at` and the manifest, then commits before `provider_dispatch` is posted. Clear the timestamp in the same transaction that records main’s proven not-dispatched result with `permit_expired`, `connection_expired` or `provider_unavailable`. An empty timestamp proves zero dispatch; a set value means dispatch may have happened, including a crash between commit and send. [ADR-0052](adr-0052-current-provider-dispatch-authorization.md) defines the transfer guards and permit policy.

### Application exit

Closing a window while another Ohtia window remains open only detaches that window's subscriptions. Closing the last window, the menu Quit command and ordinary platform quit requests use the same application-exit flow; Ohtia does not silently become a hidden background service. An operating-system shutdown or logout exits without a dialog and follows crash recovery on the next start. Editor save/discard handling remains governed by [frontend architecture](../frontend-architecture.md#manuscript-editor-boundary).

Pause new task admission while the exit decision is presented. With running work, offer these explicit actions; uncertain tasks do not open this dialog:

- **Close dialog:** dismiss exit and revalidate eligible dispatch; no task is cancelled.
- **Wait for replies, then quit:** start no further queued tasks. Let the admitted attempts finish under their existing deadlines; preserve queued tasks for the next start and retain existing blocking reasons. Explain that queued work continues at the next start. Keep the interface open for any required approval. Exit only after active outcomes, final research writes and owned local termination are recorded.
- **Cancel work and quit:** cancel queued/blocked tasks without executing them, move active tasks to `cancelling`, deny new research effects and request bounded termination. Quit normally after cancellation and cessation receipts are durable.

With no running work, complete editor/DB shutdown and exit without a work-cancellation prompt. Accepted queued work remains queued and blocked work keeps its reason. Use neither `shutdown_paused` nor a “Quit with unresolved remote work” action. Uncertain remote work remains recorded without opening a dialog or implying known usage. An orderly quit still requires owned local execution to cease and final writes to be durable; if local cessation is unproven, retain the recovery explanation, do not silently abandon owned children or descendants, and do not record a clean stop. An OS shutdown, logout, crash or forced exit uses crash recovery rather than pretending orderly cancellation.

### Restart, suspension and unresolved work

On startup, hold dispatch and reconcile persisted task/attempt receipts before scheduling. Terminal tasks stay terminal. After an ordinary orderly exit without migration recovery, accepted queued tasks continue automatically in order after revalidation and blocked tasks keep their reasons. After a crash, power loss or forced quit, all not-started tasks acquire `restart_paused`; one researcher command, “Continue all”, resumes them across projects in order after revalidating prerequisites and policy. Opening a project, enabling a connection or opening the activity panel does not clear a crash pause. Coalescing a restart-paused task preserves that pause.

Ordinary automatic continuation applies only when storage admission did not begin with a migration-recovery gate. [ADR-0010](adr-0010-pre-migration-recovery.md) and the [schema-recovery contract](../architecture.md#schema-migration-recovery-and-manuscript-delivery) prohibit automatic restart of pending provider work during recovery. A retry resolving a pre-existing gate, after rollback or checkpoint restoration, therefore applies the unclean-start hold regardless of a recorded `clean_stop_at`: not-started tasks acquire `restart_paused` and unactivated coordination intent receives its corresponding restart hold. Classify the previous run as unclean for every rule of this review, including unfinished attempts, even when its recorded stop was orderly. Cancel a proven undispatched attempt with `service_restarted` and hold its task with `restart_paused` (or cancel it under the returning-reply rule), rather than applying orderly-stop requeue; keep the dispatched/uncertain and exhausted-budget rules below. The existing “Continue all” command releases holds after revalidation; it is separate from the storage Retry action.

The durable recovery fact is the existing `migration-pending.json` in the admitted data root, validated by the storage owner before retry. Reuse its version-1 JSON format with exactly `version`, `operation`, `source` and `target`, under the existing identifier/schema checks; no restoration flag or new file is required. Capture that a valid gate preceded this admission before retry replaces or clears it. A gate first created by an otherwise healthy upgrade in the current admission does not alone require this pause. If a crash leaves that gate behind, its presence at the next admission invokes recovery.

STORY-003-008 owns the complete restart review. Its recovery handoff is a prerequisite for enabling any schema migration whose source can contain accepted tasks, in development mode as well; an earlier migration-owning story must deliver that recovery-only boundary first, including explicit continuation, rather than defer it to STORY-003-008. Integrate the review into both validated recovery-retry paths: an already committed target and a source that still needs migration. After target-schema validation and, when restoration preceded the retry, the restored database’s byte-exact activation checks, but before either path removes the gate or publishes task readiness, the data service commits task pauses and coordination holds in its reserved restart-review transaction. These are later writes to the validated active database, never changes to the immutable checkpoint or to a database still undergoing byte-exact restoration activation. Only after that commit may storage clear the gate and synchronize its directory. A crash before the hold commit retains the gate and repeats recovery; a crash after the commit retains the holds even if gate removal already completed. Later ordinary starts preserve those holds until “Continue all”; no restored orderly-stop marker or recovery Retry itself activates coordination work or sends provider requests.

For an unfinished admitted attempt, revoke stale research authority and inspect the recorded process identity, containment and provider operation. Stop identifiable surviving local execution through the supervisor. Do not infer absence from a missing PID receipt, expired lease, elapsed deadline, lost stream or the end of the previous broker process. Record exactly which local/external facts are confirmed.

If zero dispatch and applicable local cessation are proved, record the interrupted attempt `cancelled` with `service_restarted`. After an orderly stop without migration recovery, requeue its task within the original attempt/work limits; after a crash, leave it restart-paused until “Continue all”. Cancel a returning reply only if its conversation already has a not-started reply; returning consultation, contribution and synthesis tasks retain their place. If its attempt budget is exhausted, mark it `failed`; fresh work requires a new accepted task. For a provider request controlled by main, an unfinished attempt with `dispatch_permitted_at` set becomes `uncertain`, even if main might not have sent it. A cancelling attempt whose connection is closed becomes `cancelled`. Apply the adapter-specific capacity-release or quarantine evidence above. Inspect known provider state only through a declared bounded reconciliation route without starting another generation or rewriting a final outcome; unknown or lost output is never invented as a successful result or zero consumption.

Suspension is not a new attempt. On resume, recheck deadlines, authorization and process/provider state before accepting effects or dispatching further work. Use a verified suspend-aware clock or treat a detected suspend/resume interval as requiring this reconciliation; sleep must not silently extend permission or retry budgets.

A user can request fresh work despite unresolved remote completion only after local cessation is proved. The trusted human command records the unresolved task reference and explicit acknowledgement of possible duplicate external work/usage, releases that quarantine for the named replacement and creates a new linked task with newly checked inputs, policy and budget. The old task remains `uncertain`; this action neither declares it stopped nor gives its attempt new research authority. Model tools cannot issue that command. Late usage follows [ADR-0029](adr-0029-operation-profiles-and-usage-reports.md), independently of research-state finalization.

## Consequences

The work lifecycle survives interface/process loss while retaining explicit execution and cost uncertainty. The inference default permits up to ten concurrent replies, capped by each adapter, while local processing retains a separate stored limit. The researcher can choose inference parallelism without overriding provider safety constraints. SQLite stores intent and receipts; this decision does not require a hosted queue or a separate server application.

Required verification covers duplicate acceptance, both completion/cancellation orders, simultaneous slot claims and settings updates, persisted defaults/overrides, invalid concurrency values, lowering limits below occupied capacity, adapter-specific limits, quarantines across settings changes, missing policy limits, waiting-for-approval deadlines, one retry across layers/restart, spawn-before-receipt crashes, reused PIDs, descendant cessation, late results/usage, suspend/resume, all exit choices, interrupted migration quiescence and human-authorized unresolved replacements. Test every transition with deterministic processes/providers, plus real platform/runtime conformance for the cessation guarantees actually used. The operation contract must supply its numeric bounds before that producer can be enabled. Closing a provider connection can leave remote work and charges unknown. When the running-work exit dialog is shown, it explains that queued work continues at the next start. With no running work, exit introduces no additional announcement or dialog. Crash recovery requires one explicit continuation. Validate each adapter's cessation evidence at its actual native/account boundary before claiming it can release capacity.
