# Bounded foundation application port

## Scope and authority

This is the P3 contract for [STORY-001-003](epics/EPIC-001-desktop-foundation/STORY-001-003-define-and-verify-the-bounded-application-port.md), implementing [ADR-0002](adr/adr-0002-typescript-product-and-local-ipc.md) and the appearance record in [Application preferences and bootstrap](architecture.md#application-preferences-and-bootstrap). [Desktop foundation contract](desktop-foundation-contract.md) supplies D1a and the [locked developer workspace](developer-workspace.md) supplies W2 on the consumer base. The portable API carries application configuration; the provider connection operations `connection.read`, `connection.subscribe`, `connection.probe`, `connection.listModels`, `connection.connect`, `connection.replaceKey` and `connection.disconnect`, which main handles without forwarding them to the data service; and the research operations of its section “Research operations and text parts”, which main forwards to the data service. It has no filesystem, SQL or subprocess authority, and no operation returns a credential. The connect and replace-key operations of an API-key connection carry the pasted key once, from the window to main, which never forwards it to the data service. PRIN-004, PRIN-006, PRIN-007 and PRIN-016 require preserving correlation, reporting uncertain effects and distinguishing deterministic contract evidence from native or durable execution.

The runtime owner binds the private transport to actual Electron IPC and exposes only `FoundationPort` through the isolated preload. It supplies live sender-frame objects, the exact admitted packaged document URL, trusted fresh identifiers, service/window generations, monotonic timers and disposal on navigation, frame destruction or service replacement. Frame metadata comes from Electron, never an envelope. Register only admitted application main frames; subframes and external documents receive no permit. The storage owner supplies exclusive serialized transactions and durable receipts. Neither a frame object in a fixture nor an in-memory transaction establishes those native guarantees.

## Canonical schemas and resource policy

The public [contracts entry](../packages/contracts/src/index.ts) exports the complete wire types, operation input/output maps, supported locale inventory, discriminated outcomes and runtime decoders from [port.ts](../packages/contracts/src/port.ts). Protocol version is `1`; numeric policy identity is `foundation-1`. [The resource policy](../config/desktop/resource-policy.json) is the sole numeric authority. [The build projection](../tooling/port-policy.mjs) produces ignored portable TypeScript constants from that record before workspace compilation; [the unconditional CLI entry](../tooling/generate-port-policy.mjs) does the same for direct contracts-package build/typecheck, including aliased checkout paths. It rejects unsupported policy identities and missing, nonpositive, unsafe or nonfixed bounds. No manually maintained numeric table or runtime configuration overrides the record. Consumers build from the same reviewed record and run its [metadata checker](../scripts/desktop_contract.py); a policy change requires reviewed contract and corpus updates before integration.

`decodeEnvelope` takes detached data, rejects custom prototypes, accessors, symbols, unknown keys, prototype-related names, sparse arrays, nonfinite or unsafe numbers, negative zero and invalid Unicode scalar strings, and returns a copied validated envelope. `validateJsonBounds` separately exposes the policy's generic JSON complexity validation for conformance. Root depth is one; every child value increments depth and the node count. Object keys and string values have UTF-8 byte bounds; arrays and object own-key counts have count bounds. Identifiers use nonempty ASCII letters/digits followed by letters/digits/underscore/hyphen and the policy's identifier byte maximum. Finite fractional values are accepted only by the layout width schema; generic `validateJsonBounds` retains its integer-only contract. Revisions and sequences are safe nonnegative integers; sequences start at one, and replacement rejects a revision that cannot be incremented safely.

`encodeEnvelope` validates before serializing. Text transports use compact `JSON.stringify` encoding, without a BOM or insignificant whitespace. `decodeText` checks encoded size before parsing and requires identical re-encoding, rejecting duplicate keys and ambiguous number/escape spellings. `decodeUtf8` additionally rejects malformed, truncated, overlong, surrogate and out-of-range UTF-8 byte sequences. Both directions pass the same schema and size checks; no invalid child payload is forwarded as an application result. Decode failures contain controlled codes, never the rejected payload or exception text. Read-side invalid service messages become `invalid_service_result`; a potentially dispatched replacement becomes `uncertain`.

Initial request payloads also enforce the policy's input byte and field bounds; result/event payloads enforce its output byte bound. The closed status/appearance/locale shapes are intentionally smaller than these maxima. One request names one operation; arrays of operations and arbitrary preference records are rejected, enforcing the initial single-work-unit contract. The current closed event shapes hit the queue count cap before its byte cap; both checks remain active.

## Envelopes and named operations

Requests and results carry exact `protocol`, `policy`, `kind`, `requestId`, `operationId`, `windowGeneration`, `serviceGeneration`, `operation` and `payload` fields. Preload creates correlation IDs and captures admitted generations; renderer arguments cannot replace them. IDs identify work and do not authenticate a frame. A result must match every request identity field. Wrong-generation messages are discarded, and late or duplicate replies cannot revive a settled call. A revision-checked replacement success additionally matches the requested value, saved source and exactly the next revision. Execution-limit replacements use last-write-wins admission and match the requested inference value without an expected revision.

- `locale.read`, `locale.replace`, `locale.receipt` and `locale.subscribe`: the [shared interface localization contract](localization.md#named-preference-operations) defines the validated choice, effective/system snapshot, durable receipts and bounded publication. They extend this same port and preference owner.
- `status.read`: empty input, returning `FoundationStatus` with controlled artifact class, service readiness, engine readiness and the broker's resolved `interfaceLocale`. A verified engine requires a ready service. Status contains no filesystem paths or credential objects.
- `appearance.read`: empty input, returning `AppearanceRecord` with `schemaVersion`, `revision`, `value` and `source`. Values are the existing `system`, `light` and `dark` contract. A saved record has a positive revision and uses `source: saved`; a missing record uses `source: default`, revision zero and `system`. A rejected stored presentation value uses `source: invalid_fallback`, `system` and its known record revision. An unreadable revision yields a controlled failure; it cannot authorize an overwrite. Reading fallback never changes the stored value.
- `appearance.replace`: input contains exactly `expectedRevision` and `value`; the envelope's stable `operationId` identifies this replacement. A successful transaction replaces only appearance, advances its revision once and returns a saved record. Explicit replacement can repair a rejected value when its revision is known. Other preferences and research/editor state remain untouched.
- `appearance.receipt`: input contains exactly `targetOperationId`. It returns `not_found`, `pending`, or `recorded` with the original saved success or stale-revision rejection. Other errors are not recorded terminal receipt outcomes in this initial contract. It reads operation history rather than inferring an outcome from the current preference.
- `layout.read`, `layout.replace` and `layout.receipt`: the named layout preference and transactional receipt operations, with the same revision, correlation and uncertainty rules. [Workspace controller API](workspace-controller.md#persistence-and-recovery) describes their composition; [Workspace layout](workspace-layout.md#desktop-preference-boundary) owns the exact value and per-window propagation policy. Missing/invalid read records carry `null` with their source and known revision. No layout event subscription rearranges an existing window.
- `bounds.read`, `bounds.replace` and `bounds.receipt`: main-owned operations for the [native window bounds contract](epics/EPIC-002-basic-interface/epic.md#spec-002-022-integrated-title-bar-and-native-window-state), using the same record sources, revision checks and atomic receipt discipline as layout. The broker calls the supervised peer directly with trusted correlation and generation identities; renderer port admission refuses these operations and the preload exposes no bounds methods.
- `limits.read`, `limits.replace` and `limits.receipt`: the execution-limit preference operations. `limits.read` has empty input and returns the admitted service generation, the record’s revision, its `max_concurrent_inference` and the number of inference replies running. `limits.replace` input contains exactly `value`, a whole number from 1 to 50; the last accepted write wins, advances the revision by one and returns the saved record with the running count. `limits.receipt` input contains exactly `targetOperationId` and returns `not_found`, `pending` or `recorded`; a repeated `limits.replace` and a recorded receipt return the recorded value and revision with the current running count. Each accepted replacement records its receipt in the same transaction, and every window learns of it through `research.subscribe`. Local processing is unchanged. A metadata-only `inferenceActivity` notice on that same stream asks consumers to reread live counts when active work changes, including a window without an open project; it has no task identity or research content.
- `updateCheck.read`, `updateCheck.replace` and `updateCheck.receipt`: the startup update-check preference of [SPEC-001-040](epics/EPIC-001-desktop-foundation/epic.md#spec-001-040-update-check-and-notice-in-the-application), with the same record sources, revision checks and atomic receipt discipline as appearance. The value is a boolean. A missing record reads `true` with `source: default` and revision zero; an unreadable saved value reads `false` with `source: invalid_fallback` and its known revision, so a damaged record never starts a request. [Settings](settings.md#update-check-on-startup) describes the preference.
- `update.read` and `update.check`: main-owned operations with empty input that never reach the data service. Both return the broker's numbered notice `{sequence, state}`, where the update state contains `installedVersion`, `check` (`unavailable`, `idle`, `checking`, `checked` or `failed`), `failure` (`timeout`, `network`, `invalid_response` or `too_large` when `check` is `failed`, otherwise `null`) and `available` (`null` or the newer final `version`, its release `notes` and `notesTruncated`). `update.check` starts a manual check, or joins a running one, and returns at once, because the request may outlast `request_deadline_ms`: the state is `checking`, or `unavailable` for a build that cannot check. Main pushes each later state to every window on the private `ohtia:update-state` channel with the same numbering; preload drops stale or repeated sequences and exposes only `update.subscribeState`. A reply and a push travel on separate channels and may arrive in either order, so a consumer keeps the notice with the highest `sequence`. Release notes are inert text split at code points into parts of at most `string_bytes`, whose compact JSON stays within `update_notes_bytes`; longer notes are cut and marked `notesTruncated`. A development, qualification or nonfinal-version build always reports `unavailable` and makes no request.
- `layout.failureNotice`: empty input, returning exactly `{announce: boolean}`. The admitted main broker grants the first claim in its application lifetime and refuses subsequent claims across windows/service replacements. This transient announcement claim changes no saved preference.
- `status.subscribe` and `appearance.subscribe`: input and successful result contain the same fresh `subscriptionId`. A stream becomes active after its acknowledged result; its first event is a snapshot with sequence one. The producer sends the acknowledgement before events. Appearance events carry confirmed/fallback snapshots, with strictly increasing revisions after the first snapshot.

Events contain exactly `protocol`, `policy`, `kind: event`, window/service generations, `subscriptionId`, `sequence`, `topic` and the appropriate status/appearance/locale `payload`. They contain no request/operation fields. A cancellation control contains the request identity fields and `kind: cancel`, without a payload. Unsubscription contains protocol/policy, `kind: unsubscribe`, both generations and `subscriptionId`. These controls do not allocate another pending request. The runtime independently authorizes each control and resolves its target only within the registered frame/generation; it never uses an operation ID alone as a cancellation capability.

## Research operations and text parts

The [composer specification](epics/EPIC-003-research-agents/epic.md#spec-003-017-message-composer) adds `destination.read`, `conversation.stop` and `task.stop`. `destination.read` takes a project and exactly one conversation or answering agent, validates their association and returns a nullable destination with its routed operation, current attempt-duration limit and connection identity, independent of connection availability. It shares the data service’s acceptance routing; the window resolves display name and kind from the adapter’s shared declaration and account email through `connection.read`. Its compact caption identifies that service and account or API-key mode, without repeating the conversation scope or attempt duration. A project or shown-conversation change rereads the destination, including after a subscription gap. These cancellable reads do not hold timeline loading or the event queue. Send remains unavailable until the read succeeds; a failed destination or account read preserves the draft and offers an explicit refresh. Stop remains available independently of these reads. A conversation synchronization failure before destination resolution invalidates unfinished destination reads and exposes the same explicit recovery; it does not leave an idle loading state. A completed destination survives independent timeline or header failures. A subscription gap immediately invalidates it while replacement observation is pending; a lost or rejected subscription exposes the failed recovery state. Send cannot use pre-gap values. When observation is unavailable, the destination refresh first reconnects the owning conversation and retains its draft; only accepted observation followed by a successful metadata read restores readiness. A scoped project event starts its mandatory destination reread before the independent project-list refresh. Empty and over-limit Send descriptions retain their specified precedence. `conversation.stop` atomically applies the existing task Stop to every queued, blocked, running or cancelling task in that conversation and records one idempotent receipt; it preserves saved messages. `task.stop` uses its existing task-level receipt. A repeated identifier cannot stop newly accepted work. The data service rejects whitespace-only or over-20,000-code-point researcher messages with `message_invalid`, independently of the window.

The [project-setup specification](epics/EPIC-003-research-agents/epic.md#spec-003-019-project-setup-operation) exposes the proposal decisions `project.confirmSetup` and `project.rejectSetup` through this boundary. Both setup decisions take the proposal identifier and use the shared command-receipt discipline; the data service rechecks the proposal state and confirmation preconditions.

The [task-notice specification](epics/EPIC-003-research-agents/epic.md#spec-003-018-task-notices) adds `task.tryAgain`, `task.startAgain`, `usagePause.resume`, `task.continueAll` and `pause.read` to the same port. The four commands use `command_receipts` and retain their operation identifier after other failures or unconfirmed results; definitive precondition rejections save nothing and discard that intent, so another Start reply again requires a fresh confirmation; a second window may resume an already closed usage pause or continue an already released restart pause without change. Try again accepts only the conversation’s latest failed reply, except `not_eligible`, and creates a new task with `replaces_task_id`; Start reply again accepts only its latest uncertain reply after the window’s duplicate-usage confirmation. Both reject newer work and pending-limit overflow before saving. Both apply the task-notice specification’s confirmed-setup guard to fresh recovery intents, using `task_not_retryable` with `check_request`; recorded receipt replays retain their original result. A partial reply remains excluded from its replacement’s input; otherwise the replacement covers the current messages. Retrying an empty model catalog asks main to refresh it and holds dispatch until its report.

`pause.read` has empty input and returns `revision`, a global `restart` count and a `usage` array of open connection pauses with their held-task counts, including zero. The revision begins at 1 for each admitted data-service connection. Connection-local SQLite TEMP triggers advance it in the same transactions that open or close a usage pause or move a held task, including coalescing and Stop; rollback also rolls back the revision. After each committed transaction the service sends `pauseCounts` with that revision to every research subscriber, regardless of project scope. Consumers reread on an unknown revision, after a sequence gap and after every successful resume or continuation. A metadata-only `destinationChanged` event on the same stream asks the composer to reread its connection disclosure without opening another subscription. Connection-state reports and the final model page also refresh held queued tasks’ advisory `waitingForModels` and `waitingLimit` values; equal-revision merges may update only those readiness values, preserving durable task fields and ignoring older revisions.

Conversation summaries include `latestReplyTaskId`; task timeline items include connection, blocking and outcome reasons, dispatch and supersession evidence, the immutable saved-reply identity for recovery above the newest page, and their accepted policy’s duration and inactivity bounds. The window selects notices from these controlled values and the shared connection declaration, rather than parsing provider errors. ChatGPT’s usage address is the fixed `chatgptUsage` destination of `openLink`, so the window cannot supply an arbitrary address to that operation.

Research operations are named `<record>.<action>` and listed in each research feature's specification. [The conversation specification](epics/EPIC-003-research-agents/epic.md#spec-003-015-conversation-view) introduces their port boundary. Main admits them against the live frame, origin and generations, then forwards them to the data service, which validates them and rechecks their domain preconditions. Data-changing operations carry an operation identifier and record a command receipt whose hash covers their payload. Research request payloads are bounded by `research_input_bytes`; results and events remain bounded by `initial_output_bytes`, alongside every existing string, container, depth, node and complete-envelope bound.

`project.open` takes a project identity and the envelope’s operation identifier, retaining its first success or `record_not_found` result with next action `refresh_record`. `project.list` takes a null or `(lastOpenedAt, id)` cursor and a count from 1 to 40, returning whole project rows with `next` and `hasMore` in descending opening-time and identity order. The window fills its explicit batch through additional bounded reads when envelope limits shorten a response. [Project opening](storage.md#project-opening) owns the durable ordering and receipt rules. The selector refreshes its first page whenever it opens, independently of research-content revisions. Bootstrap `openConversation` restores a renderer’s initial scope and carries subscription acknowledgements. After initial restoration, an acknowledgement can update the current scope’s remembered metadata. Ready snapshots carry the active `serviceGeneration`. When storage recovers or the ready generation changes, the window resubscribes to its current scope without recording another project opening. The separate `navigateConversation` scope with a positive, increasing window-local `revision` carries explicit development-command navigation, consumed once per revision after initial restoration; an older navigation retained in the snapshot cannot replace the latest restored scope. Project creation advances and captures the window’s selection revision, superseding pending automatic restoration, and opens its result only if no later selection superseded it. A failed or superseded initial list read keeps restoration pending for the next successful first-page read; a confirmed empty list completes it without choosing a project.

Queued tasks carry the saturated `waitingLimit`, or `null` when capacity is available, and `waitingForModels`; the service refreshes these advisory fields after capacity, policy and connection events. The renderer never infers a waiting reason from a partial history page.

`conversation.read` returns requested conversations of one project with their titles, creation/update times, revisions and answering agent. The summary also carries the latest reply task identity and the currently running or cancelling task independently of loaded history. `timeline.listBefore` returns the latest items when its cursor is null, or items strictly before the cursor `(position, rank, id)`, newest first, with at most 50 requested items. Timeline identities are stable, and revisions increase: messages have revision 1 and rank 1, proposed cards rank 2, and task notices rank 3 with their task’s `state_revision`. A task notice takes `reply_position` after starting and `input_through_position` before. A proposed card takes its producing task’s reply position. Ordering compares position, then rank, then identifier, so pagination can end within a shared position without loss or repetition. `timeline.read` rereads items of one conversation by identifier. Duplicate identities never duplicate items, and older revisions are ignored.

A window holds one `research.subscribe` for its open project and shown conversation, replacing it when either changes. A window without an open project also subscribes, receiving only shared records. Each record-change event contains its kind, identity and revision: a conversation of the open project uses its revision, a timeline item of the shown conversation its timeline revision, a project revision 1 in setup and 2 after confirmation, a usage pause revision 1 while open and 2 after resumption, and execution limits their record’s revision. Reply parts are scoped to the shown conversation. Presentation, locale, connection and research fit the existing four-subscription limit. After a sequence gap, the window subscribes with a fresh identifier and rereads projects, the shown conversation, its latest timeline page, other held timeline items and active reply parts, plus any later feature’s declared reads.

Texts longer than one port string travel as at most `text_parts` parts, each the longest prefix of whole code points fitting `text_part_bytes`. Before a text-bearing command, the window sends `text.part` with `{ index, count, bytes, sha256, text }` under that command’s operation identifier, then replaces the text with `{ parts, bytes, sha256 }`. The service keeps parts only in memory per window generation and operation identifier. It joins and checks count, byte length and SHA-256 before applying the command. The command receipt’s hash covers the text’s SHA-256, so replay returns its first result even when parts are absent. Missing or mismatched parts save nothing and discard the upload; inconsistent metadata or a conflicting repeated index also discards it. Abandoned uploads expire after `staged_text_idle_ms`; command consumption, window closure, reload, generation change and service restart discard them. The service refuses uploads beyond `staged_texts_per_window` or `staged_text_bytes_per_window` without persistence.

No result carries a string beyond the string bound. A longer immutable stored text is returned as `{ source, parts, bytes, sha256 }`; `text.readPart` accepts `{ source, index }`. The window joins the parts and checks byte length and SHA-256, rereading from the first part if integrity fails. List results contain as many whole items as fit the actual port bounds, plus continuation and whether more items exist. Identifier reads preserve requested order and return unreturned identifiers. A consumer follows bounded fragments until the requested count or end; a subsequent page requires that list’s explicit button. Scrolling never requests another page.

Streamed reply parts carry sequence numbers and fit the same per-part byte bound. A missing sequence makes the window call `reply.readParts` with `{ taskId, fromSequence }`, starting at sequence 1 and continuing after the last returned part until reaching the latest sequence returned by each result. Streaming redraws occur at most ten times per second; parts are not live announcements. A saved message replaces its streaming presentation and announces its actual author once. Its language comes from the producing task’s accepted document language; unknown language remains undeclared.

Research operations return the port's errors and the research error codes. The exported `errorActions` map and `operationErrorCodes` in [port.ts](../packages/contracts/src/port.ts) are the canonical list of each research code, its next action and the operations that return it; each research feature's specification names the codes its operations add, and the change that adds them extends both maps. Research adds the next actions `resend_parts`, which sends every part of the text again under the same operation identifier, and `refresh_record`, which reads the named records again and shows their current state without repeating the command. For a research operation, `stale_revision`, whose next action stays `refresh_preference`, means the same: the window reads the named record again and shows its current state. A rejection with a research code saves nothing and writes no receipt.

## Outcomes, cancellation and receipts

Every operation returns `Outcome<T>`: either `{ok: true, value}` or `{ok: false, error}`. `PortError` carries a stable code, its exact `nextAction`, and typed `parameters`; `stale_revision` takes `currentRevision`, a research code takes the parameters its specification names, and every other error takes an empty object. The exported `errorActions` map is canonical for error/action pairs; `operationErrorCodes` declares each operation's wire error allowlist, and both are enforced by the decoder. Nondefinitive `timeout`, `cancelled`, `disposed`, `invalid_service_result` and stream-gap replies cannot be replacement outcomes: they are rejected as invalid child responses and the client preserves `uncertain`. These codes are also the initial catalog keys; locale catalogs translate their presentation, never the protocol codes or diagnostic prose. The interface-locale field admits only the product's supported identifiers. The broker owns resolution and saved-choice admission under [ADR-0024](adr/adr-0024-typed-localization-catalogs.md); the locale replacement operation accepts only a supported explicit choice or `system`, never catalog paths or OS-preference lists.

Protocol/policy/shape/authority failures reject before dispatch. `busy` rejects before acceptance; `stale_revision` requests refresh; `operation_conflict` requests reconciliation. Unavailable service, invalid child output, timeout, cancellation, storage failure, invalid saved preference, disposal and stream gaps remain distinct outcomes with their declared actions. A service may report a definitive mutation rejection only when it can prove no effect committed; lost acknowledgement or uncertain commit must return `uncertain`. `storage_failed` means a confirmed failed/rolled-back transaction, never an unknown commit. Local timeout/cancellation/disposal of a dispatched replacement always reports `uncertain`, even when a later acknowledgement arrives.

The [named preload client](../packages/preload/src/foundation-port.ts) returns cancellable `PortCall` objects and disposable subscriptions. The request deadline begins at admission and includes waiting for the reply. Expiry settles the local wait and sends best-effort cancellation; cancellation cannot establish service cessation or rollback. No method automatically repeats a mutation or generates a replacement operation ID after losing an acknowledgement. Disposing a session removes the transport listener, timers, stream queues and pending calls, and sends best-effort cancellation/unsubscription. A new generation requires a new session.

[applyAppearanceCommand](../packages/domain/src/appearance-command.ts) runs only inside a storage-owned serialized transaction with a decoded, admitted command. It checks an existing receipt before the current revision: identical expected revision/value returns the exact original outcome; different input with that operation ID returns `operation_conflict`. New commands check the expected revision, replace once, and record the original success or stale-revision outcome. The storage adapter atomically commits the preference and receipt, or rolls both back. Exceptions remain inside that transaction and become controlled storage/uncertain outcomes at the service boundary. It must not acknowledge durable success before its actual commit is established.

After `uncertain`, preserve the operation ID and exact original payload and query `appearance.receipt`. `recorded` settles that original command; `pending` requires waiting/reconciliation. `not_found` alone never authorizes a retry: the old execution must first be proven stopped or excluded by the same serialized writer, and durable receipt lookup must cover that execution. Only then may the exact original command be resubmitted with the same operation ID. Receipt identity is scoped to the admitted application store and must survive service/window generations and restart. Receipts cannot be silently evicted while their operation can be retried; any future retirement policy needs its own safe admission contract. Durable storage, concurrent writer exclusion and crash recovery are verified by the storage story, not inferred from deterministic peers.

## Admission, streams and cleanup

[PortAdmission](../packages/main/src/port-admission.ts) is shared by every window of the single broker. It matches the registered frame object and exact document URL before decoding, then matches window/service generations. Only requests enter its pending pool. It refuses duplicate pending correlation IDs and enforces the record's per-window, global and active-window limits; active-window overflow returns the canonical `window_limit` code. It reserves subscription IDs before acceptance, refuses duplicate IDs and enforces the per-frame subscription cap independently of request acknowledgements. Its aggregate reserved-stream cap is derived from the declared window count multiplied by subscriptions per window, and retains detached-frame reservations until the producer is disposed. Each admitted request supplies an idempotent `release` callback for the runtime's terminal receipt. Cancelling a UI wait or detaching a frame does not release accepted service work; release only when that request is terminal or its generation's cessation is proved. The separate idempotent `releaseSubscription` callback releases a reserved stream only after definitive creation rejection or producer disposal, including pending-creation cancellation; acknowledging the subscribe request does not release it. Detach immediately revokes sender authority, while outstanding service and subscription slots remain counted. Service replacement revokes old permits and disposes sessions before admitting new work.

Subscriptions enforce per-window count, contiguous sequence, topic, generation, queue item count and complete encoded queue bytes. Dispatch is deferred through the injected scheduler, so a slow consumer cannot create an unbounded queue. A sequence gap, event before acknowledgement, revision regression or overflow discards the queue, emits `sequence_gap` and sends unsubscription. The consumer explicitly rereads and resubscribes with a fresh ID. Invalidation walks a snapshot of the affected streams, so synchronous recovery listeners cannot repeatedly enter the same invalidation round. Unsubscription of an unknown ID is an authenticated no-op; it never creates a stream. Unsubscription is idempotent; the runtime removes producer resources even if creation was still pending, and orders or remembers cancellation so a late creation cannot resurrect a disposed subscription. Listener exceptions close the affected stream without escaping the transport callback. UI listeners return promptly; arbitrary consumer work is not interruptible by this scheduler.

## Conformance and security evidence

The reusable [corpus](../tests/fixtures/port-corpus.ts) contains accepted request/result/event/control messages and rejected protocol/policy/field/value examples. [The suite](../tests/port.test.ts) applies it through object, compact-text and UTF-8 decoders, verifies every current error/action and supported locale, and exercises the named client, synthetic frame admission and transaction peer. Consumer owners can import the corpus from this repository and run their producer/consumer against the same cases; tests remain outside packaged product outputs.

Run `python3 scripts/desktop_contract.py` and the [workspace checks](developer-workspace.md#common-commands). The `P3 shared producer/consumer conformance corpus`, `P3 bounded named bridge with deterministic transport peers`, `P3 broker admission with synthetic frame identities` and `P3 transaction/idempotency contract with deterministic non-durable peer` suites identify their enforcing portable boundary. Their scenarios cover accepted/invalid messages, wrong versions and policy, spoofed/unknown/prototype fields, strict multibyte and complexity bounds, stale revisions, invalid responses, queue saturation, cancellation/deadline races, old generations, subscription cleanup, conflicting replay and lost-acknowledgement reconciliation.

Under [Foundation security applicability](foundation-security.md), these tests provide scoped FND-INPUT evidence for ASVS `v5.0.0-2.1.1`–`2.1.3`, `2.2.1`–`2.2.3`, `15.1.3`, `15.2.2`, `15.3.5` and `15.3.6`, and portable FND-AUTHORITY evidence for the inventory's authorization group. They verify runtime schemas, resource admission, synthetic frame/generation matching and transaction contracts. Source/tree identities, test output, reviewer identities, omissions and finding resolutions belong in ignored task review evidence. Actual Electron sender identity, private channel isolation, installed artifacts on native OS/CPU targets, durable SQLite transactions and crash/restart behavior require their runtime/storage owners' enforcing-boundary evidence; portable tests establish none of those claims. No complete security, accessibility or linguistic conformance follows from this port corpus.

## Named presentation commands

[STORY-002-004](epics/EPIC-002-basic-interface/STORY-002-004-commands-native-menus-about.md) extends `DesktopBridge` with the closed `commands` surface. The [command contract](../packages/contracts/src/commands.ts) owns command IDs, localized label keys, groups, per-platform shortcut arrays, unavailable reasons, context, snapshots and intents. The registry is a per-window [CommandController](../packages/renderer/src/command-controller.ts), shared by contextual controls and native menu/keyboard intents. Preference effects continue through `FoundationPort` and its durable operation/receipt contracts; registry availability grants no storage, provider or human-confirmation authority (PRIN-002, PRIN-005 and PRIN-016).

Main recognizes application keys in Electron's `before-input-event` with the shared `commandForInput` decision and dispatches each one. On Windows and macOS it consumes the key there. On Linux it leaves the key unconsumed, and `CommandSurfaces` cancels the same key, by the same decision, in a window capture listener before any page handler. Chromium drops the character and key-release events that follow a key consumed in the browser until the next key press. An IBus XKB engine on KDE Wayland commits Latin text through text-input-v3 without key events, and Chromium delivers such a single-character commit as a character event, so a consumed shortcut would discard the letters typed next.[^chromium-keyboard-suppression][^chromium-ime-commit]

[^chromium-keyboard-suppression]: The selected widget host keeps suppressing character and key-up events after a browser-handled raw key-down until the next key-down.

[^chromium-ime-commit]: The selected Linux input method delivers an asynchronous single-character commit through `InsertChar`, which the widget host view forwards as a character event.

`context()` claims the broker-issued window-controller incarnation and platform. Claiming it revokes the previous registry, including same-document remounts; a denied foreign navigation preserves the live incarnation. `publish(snapshot)` supplies an exact complete command projection, locale and strictly advancing revision for that generation. Main validates the actual frame/origin and generation before accepting it. Native menu labels, enabled state, checked state and macOS unavailable tooltips follow the focused window. Native lifecycle actions stay in main; other menu clicks and non-edit application shortcuts enter `onIntent(listener)` as detached closed intents; its returned function removes the listener. Edit items use native responder roles. No operating-system-wide shortcuts are registered, and View zoom commands never use Electron zoom roles.

`CommandController.register(id, handler)` accepts one handler for a declared ID and returns its idempotent removal function. A handler supplies `state()` with an optional reason/checked value and `run(execution)` returning a boolean or its promise. Recheck availability on invocation. Unregistered commands expose `handler_missing`; they have no placeholder action. `invoke(id)` allocates a local presentation intent; `receive(intent)` accepts a native intent. Each source has a monotonic sequence: an exact latest duplicate shares its result, conflicting/reordered sequences are rejected, and older delivery never repeats the effect. This bounded presentation deduplication does not replace durable preference receipts.

The execution supplies its originating context and `isCurrent()`. Check that lease, plus any dialog/selection incarnation, before applying asynchronous view results. Removing a handler or disposing its controller revokes the result without undoing an already accepted effect. `changed()` republishes availability after a controller change; `setLocale()` updates the same registry without remounting its views. `subscribe()` returns a removal function, and `dispose()` removes all registry handlers/listeners. Results distinguish completed, unavailable, failed, revoked, unknown command, stale context and stale intent. Completed means that the handler reported completion, not that a domain mutation became durable.

Registration ownership uses a unique registration record rather than the handler object, so disposing and re-registering the same object cannot revive an old execution. Main owns Quit and Close through the admitted foundation lifecycle, independently of renderer availability or composition. Keyboard intents recheck availability in the current registry; a delayed menu mirror cannot veto a now-available keyboard intent. Native menu projection is rebuilt only when its observable state or focused window changes. Unknown theme selection remains a disabled ordinary item until the handlers supply one complete, confirmed `checked` selection, avoiding the native radio group's automatic first selection.

Effect-bearing named broker requests and About reads share the same per-frame and aggregate `RequestBudget` as `PortAdmission`; accepted work retains its slot until terminal completion, including after frame disposal. Session/context and projection controls complete synchronously without a request slot, like the existing frame handshake and cancellation controls. No second request pool multiplies the policy limits.

`CommandController.subscribeResults((result, command) => ...)` reports each admitted intent’s outcome once, preserves deduplication across repeated delivery and revokes observers with the registry lifetime. `CommandSurfaces` renders unavailable reasons in the active modal or window; its Settings renderer receives that feedback as a fourth argument. Its fifth Settings-renderer argument supplies an explicit return-focus owner. The optional `renderFeedback(openSettings, inDialog)` slot places feature-owned notices in the current window or Help/About dialog and uses the existing modal handoff when a notice opens Settings.

`CommandSurfaces` owns the Help/About handlers and accepts a stable `registerHandlers(controller, reason)` composition callback returning its cleanup function. Feature owners register their real Settings, workspace, theme, zoom, window, menu, palette and shortcuts handlers there. Preserve the callback identity while its controller lifetime remains the same. The supplied `reason(command)` checks the composition’s modal, focus and composition context; feature handlers add their own availability checks. An asynchronous handler may report a controlled unavailable result when trusted admission refuses an operation after its initial availability check. Replacing the bridge or registration callback starts a fresh composition lifetime and dismisses its old passive dialogs. Help closes and restores its origin before its Keyboard shortcuts button invokes the registered consumer; only that explicit handoff can bypass the old Help modal reason, and invocation still rechecks availability. Native broker operations remain closed: `perform()` admits only its declared window/edit/project-link actions; `openLink()` accepts a project destination ID rather than a URL. `openExternalLink(url)` accepts the address of a link in a rendered agent message; main parses it again with the WHATWG URL parser and opens it in the system browser only when it is at most 4,096 bytes and its scheme is `https`, `http` or `mailto`. `copyMessage(messageId)` accepts a message identifier, never text: main reads that message’s original text from the data service, writes it to the clipboard and verifies a readback before returning success. It resolves the identifier within the originating window’s open conversation, reads long text with `text.readPart` and checks its byte length and SHA-256 before copying; a changed frame, window generation, conversation or service generation revokes the operation before the native clipboard write is initiated, and a later change prevents a success acknowledgement. `about()` returns trusted running-artifact information and bundled notices. `copyVersionInformation(locale)` generates only the displayed product/version/build/system text for that validated interface locale, awaits the real clipboard write and verifies a readback before returning success. It accepts no caller-supplied text or private diagnostic payload.

The [native command acceptance helper](../tooling/command-acceptance.mjs), invoked by `desktop:test`, checks the actual assembled metadata, menu availability, offline dialogs, clipboard, keyboard route, focus, raster bounds and native viewport/zoom geometry. Its result retains omissions for physical keyboard layouts, OS IMEs and manual assistive journeys. Synthetic input vectors cover shifted punctuation and Hangul command-key values; they do not qualify an OS keyboard layout. A shifted slash invokes Keyboard shortcuts rather than silently becoming Help; the separate Help chord can be unproducible on such layouts. AZERTY top-row Ctrl+0 is likewise not silently remapped to Ctrl+Shift+0; these layout gaps require qualification and remain reachable through the menus when their handlers are delivered. [Native interface qualification](epics/EPIC-002-basic-interface/STORY-002-010-native-interface-qualification.md) owns the broader integrated qualification; deterministic adapter tests and catalog screenshots remain separate evidence.

The [Settings preference consumer](settings.md#named-preference-boundary) adds generation-bound presentation snapshots, named replacement and receipt operations for characters, zoom, source quote length and entry text length, application-wide zoom admission and a rendering-only zoom retry to this same port.

## Native window command bridge

`CommandBridge.windowAction` accepts a closed `WindowCommandRequest`: one admitted `CommandIntent` naming `window.new` or `menu.open`, plus, for `menu.open` only, an integer CSS-pixel `{x, y}` anchor and the `keyboard` or `pointer` input that activated it. Main validates the sender/frame/origin, request budget and current registry lease before applying either effect. Each source retains its last sequence and result; an identical delivery shares that result, an older or conflicting delivery is refused, and replacing the lease revokes queued effects. A window-limit refusal returns the existing localized `window_limit` reason. These presentation actions grant no preference, research or provider authority.

The application-menu handler projects the same named menu into `Menu.popup`, converts the button anchor to DIP using the originating web contents zoom and confines it to the content bounds. The renderer records the latest activation input: a pointer press is `pointer`; a key press, or a click without a press as dispatched by keyboard or assistive-technology activation, is `keyboard`. Keyboard activation passes Electron's `keyboard` menu source type, with which the menu opens with its first item selected on Windows and Linux, so that keyboard and screen-reader focus enter the menu; pointer activation keeps Electron's default source type and opens the menu without a selection. Menu dismissal settles the invocation; the renderer returns focus to the menu button when its lease remains current and no dialog has taken focus. macOS retains its system menu bar. The registered keyboard dispatcher handles application accelerators independently of menu-bar visibility; composition, AltGr and consumed presentation commands retain their existing guards.

## Provider connections

[STORY-003-001](epics/EPIC-003-research-agents/STORY-003-001-provider-adapter-contract-and-credential-store.md) extends the existing port with the schemas in [connections.ts](../packages/contracts/src/connections.ts). Each operation takes a connection code; `connection.subscribe` also takes the subscription identifier. Connect and probe return their immediate snapshots; later changes use the sequenced `connection` topic. The snapshot includes the closed state/reason pair, the declared `display_name`, `last_account_email` (the remembered registration email or `null`), `account_email` (the active session’s email or `null`), `probing`, `probe_id`, nullable `model_list_revision` and `model_count`. A completed probe emits one `probe_result` with `listed` or `unreachable`, the same probe identifier and the current list revision, without model entries. The canonical resource policy owns the probe deadline.

`connection.listModels` takes the connection, positive list revision, zero-based cursor and a count from 1 to 128. Its result contains `models`, `nextCursor` and `hasMore`, preserving the stored order. Each [`ProviderModel`](../packages/contracts/src/connections.ts) contains `id` and `name` and can carry effort support, declared levels and a default level, maximum output, provenance and retirement metadata. Main validates each complete list before replacement, admitting every entry only if it fits alone in a page. Page construction tests the complete result envelope against all wire bounds and reserves maximum-length correlation identifiers. A stale read returns `stale_revision` with `currentRevision`; zero means no list exists. Consumers restart at cursor zero for a new revision and read until `hasMore` is false before displaying a complete list. No connection operation writes a command receipt.

`connection.connect` accepts the optional boolean `new_registration`; `true` requests a new account registration without replacing the remembered account before identity validation. Omission and `false` reuse the stored registration. The [ChatGPT connection specification](epics/EPIC-003-research-agents/epic.md#spec-003-007-sign-in-with-chatgpt) owns sign-in, cancellation, timeout, session renewal and account replacement. These controls implement PRIN-011 and PRIN-016 without requiring an Ohtia account.

Main projects state and complete model lists onto the [private service channel](../packages/contracts/src/service-connections.ts) using bounded pages; the data service exposes a replacement list only after receiving its final page. A missing or incomplete model list is `null`, distinct from a complete empty list. Only `connected` permits task admission. Main explicitly excludes `last_account_email`, `account_email` and `display_name` from that private projection, and its decoder rejects them. A returning sign-in can report an updated account email in memory without changing the remembered registration; a restored session uses the registration’s last validated email. Email is persisted only in the operating-system registration entry, never in the session, database, research records or diagnostics. Credential/session types exist solely in main. The [provider conformance suite](../tests/fixtures/provider-conformance.ts) is reusable by each future adapter. The fake provider has synthetic in-memory credentials, is hidden from graphical inventories and is loaded only by the development build in development mode or by tests.

Model-list refresh requests carry a service-generation-scoped `refresh_id`. Main echoes it on the connection reports produced after receiving that request; ordinary reports cannot acknowledge an outstanding refresh. The utility retains the queue hold until the matching non-probing report, then still waits for complete model pages.
