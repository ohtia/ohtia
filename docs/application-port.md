# Bounded foundation application port

## Scope and authority

This is the P3 contract for [STORY-001-003](epics/EPIC-001-desktop-foundation/STORY-001-003-define-and-verify-the-bounded-application-port.md), implementing [ADR-0002](adr/adr-0002-typescript-product-and-local-ipc.md) and the appearance record in [Application preferences and bootstrap](architecture.md#application-preferences-and-bootstrap). [Desktop foundation contract](desktop-foundation-contract.md) supplies D1a and the [locked developer workspace](developer-workspace.md) supplies W2 on the consumer base. The portable API carries application configuration and the provider connection operations `connection.read`, `connection.subscribe`, `connection.probe`, `connection.listModels`, `connection.connect` and `connection.disconnect`, which main handles without forwarding them to the data service; it has no project, research, credential, filesystem, SQL or subprocess authority, and no operation returns a credential. PRIN-004, PRIN-006, PRIN-007 and PRIN-016 require preserving correlation, reporting uncertain effects and distinguishing deterministic contract evidence from native or durable execution.

The runtime owner binds the private transport to actual Electron IPC and exposes only `FoundationPort` through the isolated preload. It supplies live sender-frame objects, the exact admitted packaged document URL, trusted fresh identifiers, service/window generations, monotonic timers and disposal on navigation, frame destruction or service replacement. Frame metadata comes from Electron, never an envelope. Register only admitted application main frames; subframes and external documents receive no permit. The storage owner supplies exclusive serialized transactions and durable receipts. Neither a frame object in a fixture nor an in-memory transaction establishes those native guarantees.

## Canonical schemas and resource policy

The public [contracts entry](../packages/contracts/src/index.ts) exports the complete wire types, operation input/output maps, supported locale inventory, discriminated outcomes and runtime decoders from [port.ts](../packages/contracts/src/port.ts). Protocol version is `1`; numeric policy identity is `foundation-1`. [The resource policy](../config/desktop/resource-policy.json) is the sole numeric authority. [The build projection](../tooling/port-policy.mjs) produces ignored portable TypeScript constants from that record before workspace compilation; [the unconditional CLI entry](../tooling/generate-port-policy.mjs) does the same for direct contracts-package build/typecheck, including aliased checkout paths. It rejects unsupported policy identities and missing, nonpositive, unsafe or nonfixed bounds. No manually maintained numeric table or runtime configuration overrides the record. Consumers build from the same reviewed record and run its [metadata checker](../scripts/desktop_contract.py); a policy change requires reviewed contract and corpus updates before integration.

`decodeEnvelope` takes detached data, rejects custom prototypes, accessors, symbols, unknown keys, prototype-related names, sparse arrays, nonfinite or unsafe numbers, negative zero and invalid Unicode scalar strings, and returns a copied validated envelope. `validateJsonBounds` separately exposes the policy's generic JSON complexity validation for conformance. Root depth is one; every child value increments depth and the node count. Object keys and string values have UTF-8 byte bounds; arrays and object own-key counts have count bounds. Identifiers use nonempty ASCII letters/digits followed by letters/digits/underscore/hyphen and the policy's identifier byte maximum. Finite fractional values are accepted only by the layout width schema; generic `validateJsonBounds` retains its integer-only contract. Revisions and sequences are safe nonnegative integers; sequences start at one, and replacement rejects a revision that cannot be incremented safely.

`encodeEnvelope` validates before serializing. Text transports use compact `JSON.stringify` encoding, without a BOM or insignificant whitespace. `decodeText` checks encoded size before parsing and requires identical re-encoding, rejecting duplicate keys and ambiguous number/escape spellings. `decodeUtf8` additionally rejects malformed, truncated, overlong, surrogate and out-of-range UTF-8 byte sequences. Both directions pass the same schema and size checks; no invalid child payload is forwarded as an application result. Decode failures contain controlled codes, never the rejected payload or exception text. Read-side invalid service messages become `invalid_service_result`; a potentially dispatched replacement becomes `uncertain`.

Initial request payloads also enforce the policy's input byte and field bounds; result/event payloads enforce its output byte bound. The closed status/appearance/locale shapes are intentionally smaller than these maxima. One request names one operation; arrays of operations and arbitrary preference records are rejected, enforcing the initial single-work-unit contract. The current closed event shapes hit the queue count cap before its byte cap; both checks remain active.

## Envelopes and named operations

Requests and results carry exact `protocol`, `policy`, `kind`, `requestId`, `operationId`, `windowGeneration`, `serviceGeneration`, `operation` and `payload` fields. Preload creates correlation IDs and captures admitted generations; renderer arguments cannot replace them. IDs identify work and do not authenticate a frame. A result must match every request identity field. Wrong-generation messages are discarded, and late or duplicate replies cannot revive a settled call. A replacement success additionally matches the requested value, saved source and exactly the next revision.

- `locale.read`, `locale.replace`, `locale.receipt` and `locale.subscribe`: the [shared interface localization contract](localization.md#named-preference-operations) defines the validated choice, effective/system snapshot, durable receipts and bounded publication. They extend this same port and preference owner.
- `status.read`: empty input, returning `FoundationStatus` with controlled artifact class, service readiness, engine readiness and the broker's resolved `interfaceLocale`. A verified engine requires a ready service. Status contains no filesystem paths or credential objects.
- `appearance.read`: empty input, returning `AppearanceRecord` with `schemaVersion`, `revision`, `value` and `source`. Values are the existing `system`, `light` and `dark` contract. A saved record has a positive revision and uses `source: saved`; a missing record uses `source: default`, revision zero and `system`. A rejected stored presentation value uses `source: invalid_fallback`, `system` and its known record revision. An unreadable revision yields a controlled failure; it cannot authorize an overwrite. Reading fallback never changes the stored value.
- `appearance.replace`: input contains exactly `expectedRevision` and `value`; the envelope's stable `operationId` identifies this replacement. A successful transaction replaces only appearance, advances its revision once and returns a saved record. Explicit replacement can repair a rejected value when its revision is known. Other preferences and research/editor state remain untouched.
- `appearance.receipt`: input contains exactly `targetOperationId`. It returns `not_found`, `pending`, or `recorded` with the original saved success or stale-revision rejection. Other errors are not recorded terminal receipt outcomes in this initial contract. It reads operation history rather than inferring an outcome from the current preference.
- `layout.read`, `layout.replace` and `layout.receipt`: the named layout preference and transactional receipt operations, with the same revision, correlation and uncertainty rules. [Workspace controller API](workspace-controller.md#persistence-and-recovery) describes their composition; [Workspace layout](workspace-layout.md#desktop-preference-boundary) owns the exact value and per-window propagation policy. Missing/invalid read records carry `null` with their source and known revision. No layout event subscription rearranges an existing window.
- `bounds.read`, `bounds.replace` and `bounds.receipt`: main-owned operations for the [native window bounds contract](epics/EPIC-002-basic-interface/epic.md#spec-002-022-integrated-title-bar-and-native-window-state), using the same record sources, revision checks and atomic receipt discipline as layout. The broker calls the supervised peer directly with trusted correlation and generation identities; renderer port admission refuses these operations and the preload exposes no bounds methods.
- `layout.failureNotice`: empty input, returning exactly `{announce: boolean}`. The admitted main broker grants the first claim in its application lifetime and refuses subsequent claims across windows/service replacements. This transient announcement claim changes no saved preference.
- `status.subscribe` and `appearance.subscribe`: input and successful result contain the same fresh `subscriptionId`. A stream becomes active after its acknowledged result; its first event is a snapshot with sequence one. The producer sends the acknowledgement before events. Appearance events carry confirmed/fallback snapshots, with strictly increasing revisions after the first snapshot.

Events contain exactly `protocol`, `policy`, `kind: event`, window/service generations, `subscriptionId`, `sequence`, `topic` and the appropriate status/appearance/locale `payload`. They contain no request/operation fields. A cancellation control contains the request identity fields and `kind: cancel`, without a payload. Unsubscription contains protocol/policy, `kind: unsubscribe`, both generations and `subscriptionId`. These controls do not allocate another pending request. The runtime independently authorizes each control and resolves its target only within the registered frame/generation; it never uses an operation ID alone as a cancellation capability.

## Outcomes, cancellation and receipts

Every operation returns `Outcome<T>`: either `{ok: true, value}` or `{ok: false, error}`. `PortError` carries a stable code, its exact `nextAction`, and typed `parameters`; only `stale_revision` takes `currentRevision`, and every other current error takes an empty object. The exported `errorActions` map is canonical for error/action pairs; `operationErrorCodes` declares each operation's wire error allowlist, and both are enforced by the decoder. Nondefinitive `timeout`, `cancelled`, `disposed`, `invalid_service_result` and stream-gap replies cannot be replacement outcomes: they are rejected as invalid child responses and the client preserves `uncertain`. These codes are also the initial catalog keys; locale catalogs translate their presentation, never the protocol codes or diagnostic prose. The interface-locale field admits only the product's supported identifiers. The broker owns resolution and saved-choice admission under [ADR-0024](adr/adr-0024-typed-localization-catalogs.md); the locale replacement operation accepts only a supported explicit choice or `system`, never catalog paths or OS-preference lists.

Protocol/policy/shape/authority failures reject before dispatch. `busy` rejects before acceptance; `stale_revision` requests refresh; `operation_conflict` requests reconciliation. Unavailable service, invalid child output, timeout, cancellation, storage failure, invalid saved preference, disposal and stream gaps remain distinct outcomes with their declared actions. A service may report a definitive mutation rejection only when it can prove no effect committed; lost acknowledgement or uncertain commit must return `uncertain`. `storage_failed` means a confirmed failed/rolled-back transaction, never an unknown commit. Local timeout/cancellation/disposal of a dispatched replacement always reports `uncertain`, even when a later acknowledgement arrives.

The [named preload client](../packages/preload/src/foundation-port.ts) returns cancellable `PortCall` objects and disposable subscriptions. The request deadline begins at admission and includes waiting for the reply. Expiry settles the local wait and sends best-effort cancellation; cancellation cannot establish service cessation or rollback. No method automatically repeats a mutation or generates a replacement operation ID after losing an acknowledgement. Disposing a session removes the transport listener, timers, stream queues and pending calls, and sends best-effort cancellation/unsubscription. A new generation requires a new session.

[applyAppearanceCommand](../packages/domain/src/appearance-command.ts) runs only inside a storage-owned serialized transaction with a decoded, admitted command. It checks an existing receipt before the current revision: identical expected revision/value returns the exact original outcome; different input with that operation ID returns `operation_conflict`. New commands check the expected revision, replace once, and record the original success or stale-revision outcome. The storage adapter atomically commits the preference and receipt, or rolls both back. Exceptions remain inside that transaction and become controlled storage/uncertain outcomes at the service boundary. It must not acknowledge durable success before its actual commit is established.

After `uncertain`, preserve the operation ID and exact original payload and query `appearance.receipt`. `recorded` settles that original command; `pending` requires waiting/reconciliation. `not_found` alone never authorizes a retry: the old execution must first be proven stopped or excluded by the same serialized writer, and durable receipt lookup must cover that execution. Only then may the exact original command be resubmitted with the same operation ID. Receipt identity is scoped to the admitted application store and must survive service/window generations and restart. Receipts cannot be silently evicted while their operation can be retried; any future retirement policy needs its own safe admission contract. Durable storage, concurrent writer exclusion and crash recovery are verified by the storage story, not inferred from deterministic peers.

## Admission, streams and cleanup

[PortAdmission](../packages/main/src/port-admission.ts) is shared by every window of the single broker. It matches the registered frame object and exact document URL before decoding, then matches window/service generations. Only requests enter its pending pool. It refuses duplicate pending correlation IDs and enforces the record's per-window, global and active-window limits; active-window overflow returns the canonical `window_limit` code. It reserves subscription IDs before acceptance, refuses duplicate IDs and enforces the per-frame subscription cap independently of request acknowledgements. Its aggregate reserved-stream cap is derived from the declared window count multiplied by subscriptions per window, and retains detached-frame reservations until the producer is disposed. Each admitted request supplies an idempotent `release` callback for the runtime's terminal receipt. Cancelling a UI wait or detaching a frame does not release accepted service work; release only when that request is terminal or its generation's cessation is proved. The separate idempotent `releaseSubscription` callback releases a reserved stream only after definitive creation rejection or producer disposal, including pending-creation cancellation; acknowledging the subscribe request does not release it. Detach immediately revokes sender authority, while outstanding service and subscription slots remain counted. Service replacement revokes old permits and disposes sessions before admitting new work.

Subscriptions enforce per-window count, contiguous sequence, topic, generation, queue item count and complete encoded queue bytes. Dispatch is deferred through the injected scheduler, so a slow consumer cannot create an unbounded queue. A sequence gap, event before acknowledgement, revision regression or overflow discards the queue, emits `sequence_gap` and sends unsubscription. The consumer explicitly rereads and resubscribes with a fresh ID. Invalidation walks a snapshot of the affected streams, so synchronous recovery listeners cannot repeatedly enter the same invalidation round. Unsubscription of an unknown ID is an authenticated no-op; it never creates a stream. Unsubscription is idempotent; the runtime removes producer resources even if creation was still pending, and orders or remembers cancellation so a late creation cannot resurrect a disposed subscription. Listener exceptions close the affected stream without escaping the transport callback. UI listeners return promptly; arbitrary consumer work is not interruptible by this scheduler.

## Named presentation commands

[STORY-002-004](epics/EPIC-002-basic-interface/STORY-002-004-commands-native-menus-about.md) extends `DesktopBridge` with the closed `commands` surface. The [command contract](../packages/contracts/src/commands.ts) owns command IDs, localized label keys, groups, per-platform shortcut arrays, unavailable reasons, context, snapshots and intents. The registry is a per-window [CommandController](../packages/renderer/src/command-controller.ts), shared by contextual controls and native menu/keyboard intents. Preference effects continue through `FoundationPort` and its durable operation/receipt contracts; registry availability grants no storage, provider or human-confirmation authority (PRIN-002, PRIN-005 and PRIN-016).

Main recognizes application keys in Electron's `before-input-event` with the shared `commandForInput` decision and dispatches each one. On Windows and macOS it consumes the key there. On Linux it leaves the key unconsumed, and `CommandSurfaces` cancels the same key, by the same decision, in a window capture listener before any page handler. Chromium drops the character and key-release events that follow a key consumed in the browser until the next key press. An IBus XKB engine on KDE Wayland commits Latin text through text-input-v3 without key events, and Chromium delivers such a single-character commit as a character event, so a consumed shortcut would discard the letters typed next.[^chromium-keyboard-suppression][^chromium-ime-commit]

[^chromium-keyboard-suppression]: The selected widget host keeps suppressing character and key-up events after a browser-handled raw key-down until the next key-down.

[^chromium-ime-commit]: The selected Linux input method delivers an asynchronous single-character commit through `InsertChar`, which the widget host view forwards as a character event.

`context()` claims the broker-issued window-controller incarnation and platform. Claiming it revokes the previous registry, including same-document remounts; a denied foreign navigation preserves the live incarnation. `publish(snapshot)` supplies an exact complete command projection, locale and strictly advancing revision for that generation. Main validates the actual frame/origin and generation before accepting it. Native menu labels, enabled state, checked state and macOS unavailable tooltips follow the focused window. Native lifecycle actions stay in main; other menu clicks and non-edit application shortcuts enter `onIntent(listener)` as detached closed intents; its returned function removes the listener. Edit items use native responder roles. No operating-system-wide shortcuts are registered, and View zoom commands never use Electron zoom roles.

`CommandController.register(id, handler)` accepts one handler for a declared ID and returns its idempotent removal function. A handler supplies `state()` with an optional reason/checked value and `run(execution)` returning a boolean or its promise. Recheck availability on invocation. Unregistered commands expose `handler_missing`; they have no placeholder action. `invoke(id)` allocates a local presentation intent; `receive(intent)` accepts a native intent. Each source has a monotonic sequence: an exact latest duplicate shares its result, conflicting/reordered sequences are rejected, and older delivery never repeats the effect. This bounded presentation deduplication does not replace durable preference receipts.

The execution supplies its originating context and `isCurrent()`. Check that lease, plus any dialog/selection incarnation, before applying asynchronous view results. Removing a handler or disposing its controller revokes the result without undoing an already accepted effect. `changed()` republishes availability after a controller change; `setLocale()` updates the same registry without remounting its views. `subscribe()` returns a removal function, and `dispose()` removes all registry handlers/listeners. Results distinguish completed, unavailable, failed, revoked, unknown command, stale context and stale intent. Completed means that the handler reported completion, not that a domain mutation became durable.

Registration ownership uses a unique registration record rather than the handler object, so disposing and re-registering the same object cannot revive an old execution. Main owns Quit and Close through the admitted foundation lifecycle, independently of renderer availability or composition. Keyboard intents recheck availability in the current registry; a delayed menu mirror cannot veto a now-available keyboard intent. Native menu projection is rebuilt only when its observable state or focused window changes. Unknown theme selection remains a disabled ordinary item until the handlers supply one complete, confirmed `checked` selection, avoiding the native radio group's automatic first selection.

Effect-bearing named broker requests and About reads share the same per-frame and aggregate `RequestBudget` as `PortAdmission`; accepted work retains its slot until terminal completion, including after frame disposal. Session/context and projection controls complete synchronously without a request slot, like the existing frame handshake and cancellation controls. No second request pool multiplies the policy limits.

`CommandController.subscribeResults((result, command) => ...)` reports each admitted intent’s outcome once, preserves deduplication across repeated delivery and revokes observers with the registry lifetime. `CommandSurfaces` renders unavailable reasons in the active modal or window; its Settings renderer receives that feedback as a fourth argument. Its fifth Settings-renderer argument supplies an explicit return-focus owner. The optional `renderFeedback(openSettings, inDialog)` slot places feature-owned notices in the current window or Help/About dialog and uses the existing modal handoff when a notice opens Settings.

`CommandSurfaces` owns the Help/About handlers and accepts a stable `registerHandlers(controller, reason)` composition callback returning its cleanup function. Feature owners register their real Settings, workspace, theme, zoom, window, menu, palette and shortcuts handlers there. Preserve the callback identity while its controller lifetime remains the same. The supplied `reason(command)` checks the composition’s modal, focus and composition context; feature handlers add their own availability checks. An asynchronous handler may report a controlled unavailable result when trusted admission refuses an operation after its initial availability check. Replacing the bridge or registration callback starts a fresh composition lifetime and dismisses its old passive dialogs. Help closes and restores its origin before its Keyboard shortcuts button invokes the registered consumer; only that explicit handoff can bypass the old Help modal reason, and invocation still rechecks availability. ## Native window command bridge

`CommandBridge.windowAction` accepts a closed `WindowCommandRequest`: one admitted `CommandIntent` naming `window.new` or `menu.open`, plus, for `menu.open` only, an integer CSS-pixel `{x, y}` anchor and the `keyboard` or `pointer` input that activated it. Main validates the sender/frame/origin, request budget and current registry lease before applying either effect. Each source retains its last sequence and result; an identical delivery shares that result, an older or conflicting delivery is refused, and replacing the lease revokes queued effects. A window-limit refusal returns the existing localized `window_limit` reason. These presentation actions grant no preference, research or provider authority.

The application-menu handler projects the same named menu into `Menu.popup`, converts the button anchor to DIP using the originating web contents zoom and confines it to the content bounds. The renderer records the latest activation input: a pointer press is `pointer`; a key press, or a click without a press as dispatched by keyboard or assistive-technology activation, is `keyboard`. Keyboard activation passes Electron's `keyboard` menu source type, with which the menu opens with its first item selected on Windows and Linux, so that keyboard and screen-reader focus enter the menu; pointer activation keeps Electron's default source type and opens the menu without a selection. Menu dismissal settles the invocation; the renderer returns focus to the menu button when its lease remains current and no dialog has taken focus. macOS retains its system menu bar. The registered keyboard dispatcher handles application accelerators independently of menu-bar visibility; composition, AltGr and consumed presentation commands retain their existing guards.

## Provider connections

[STORY-003-001](epics/EPIC-003-research-agents/STORY-003-001-provider-adapter-contract-and-credential-store.md) extends the existing port with the schemas in [connections.ts](../packages/contracts/src/connections.ts). Each operation takes a connection code; `connection.subscribe` also takes the subscription identifier. Connect and probe return their immediate snapshots; later changes use the sequenced `connection` topic. The snapshot includes the closed state/reason pair, `probing`, `probe_id`, nullable `model_list_revision` and `model_count`. A completed probe emits one `probe_result` with `listed` or `unreachable`, the same probe identifier and the current list revision, without model entries. The canonical resource policy owns the probe deadline.

`connection.listModels` takes the connection, positive list revision, zero-based cursor and a count from 1 to 128. Its result contains `models`, `nextCursor` and `hasMore`, preserving the stored order. Each model contains only `id` and `name`. Main validates each complete list before replacement, admitting every entry only if it fits alone in a page. Page construction tests the complete result envelope against all wire bounds and reserves maximum-length correlation identifiers. A stale read returns `stale_revision` with `currentRevision`; zero means no list exists. Consumers restart at cursor zero for a new revision and read until `hasMore` is false before displaying a complete list. No connection operation writes a command receipt.

Main projects state and complete model lists onto the [private service channel](../packages/contracts/src/service-connections.ts) using bounded pages; the data service exposes a replacement list only after receiving its final page. A missing or incomplete model list is `null`, distinct from a complete empty list. Only `connected` permits task admission. Credential/session types exist solely in main. The [provider conformance suite](../tests/fixtures/provider-conformance.ts) is reusable by each future adapter. The fake provider has synthetic in-memory credentials, is hidden from graphical inventories and is loaded only by the development build in development mode or by tests.
