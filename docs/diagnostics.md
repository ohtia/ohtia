# Content-free broker diagnostics

## Ownership and event inventory

[ADR-0013](adr/adr-0013-private-content-free-structured-logging.md) owns the complete local file contract and OpenTelemetry mapping. [STORY-001-006](epics/EPIC-001-desktop-foundation/STORY-001-006-implement-bounded-diagnostics-without-private-content.md) implements that boundary after the [application port](application-port.md), [isolated runtime](desktop-runtime.md) and [durable store](storage.md). PRIN-004, PRIN-006, PRIN-007 and PRIN-013 require authentic artifact identity, honest uncertainty and protection of durable research when logging fails.

The [portable catalog and decoders](../packages/contracts/src/diagnostics.ts) are the executable event inventory. Each event fixes component, operation, outcome, severity and permitted error codes. Broker events cover application startup/shutdown/fatal failure, service readiness/unavailability and rejected port admission. Data-service events cover storage opening/failure/checkpoint restoration, appearance replacement success/failure/uncertainty, project creation/setup confirmation, conversation start/rename, message append and the three research reads. Research failures and uncertain outcomes have separate catalog events and carry only a closed error code. The research event privacy boundary permits no payload, operation or entity identifier, title, content, language value or provider text; successful replays report the operation outcome without implying that another record was created. Diagnostic delivery failure does not change the command result. The real-SQLite research tests check the emitted events against the catalog and private-content markers. Execution-limit reads, replacements and receipt reads emit `ohtia.limits.read`, `ohtia.limits.replaced` and `ohtia.limits.receipt_read`; failures emit `ohtia.limits.failed` with a closed error code. Their privacy review permits no operation identity, preference value, running count, research text, service/account identity or provider payload. These events carry only their catalog identity and the permitted failure code. Actual event time is optional; observed time is assigned by the broker. Broker-owned UUID correlations identify dispatched appearance requests without retaining renderer identifiers. Task acceptance, committed dispatch permits, readmission and final outcomes use closed events without task or attempt identities. They are emitted only after their storage transaction commits. They carry no prompt, response, tool argument, title, memory text, credential, model name, transfer manifest or provider error message. These events preserve the same private-content boundary while exposing durable execution outcomes.

The utility submits a private generation-bound diagnostic envelope to its supervisor. The supervisor validates its exact shape and permits only data-service events from its current live child. Child-provided resources, observed time, severity, correlation, entity identifiers and metadata bags are refused. The broker constructs resource identity from the running artifact's declared version. It reports invalid inputs through a saturating rejection counter without retaining their payload. Expected appearance errors are mapped only from validated result codes; thrown exceptions never supply diagnostic fields.

JavaScript stdout/stderr capture is suppressed in the main and utility entries before runtime work; Automatic stream output is discarded; Node may format console arguments before the suppressed write, so this does not claim that custom console formatters never run. Runtime failures become fixed codes or controlled service exit. The development launcher ignores native stdout/stderr, the utility uses ignored stdio and its environment is restricted. The dependency inventory introduces no analytics SDK, tracing exporter or crash reporter. Browser resources have no network capability. These boundaries do not claim to suppress OS crash facilities outside Ohtia's control. No diagnostic content is transmitted automatically.

## Files, admission and operations

The [writer](../packages/main/src/diagnostic-writer.ts) receives only the admitted canonical research root. The broker verifies the isolated profile's stable sentinels and [data-directory admission](../packages/main/src/locator.ts) before log I/O. An invalid locator leaves graphical bootstrap diagnostics without a fallback log directory. Workers have no log file handles. The existing native broker lock supplies cross-process ownership; the writer also refuses a second instance for the same directory inside one process.

The ADR owns the five-file/5-MiB retention policy. The writer validates a record before enqueuing its encoded bytes; its additional fixed limits are 8,192 bytes per record, 64 pending operations and 64 scanned records per read page. The present closed vocabulary encodes only ASCII records, including versions, UUIDs and timestamps. Multibyte untrusted input is refused, while Unicode native paths are exercised separately. Startup and read buffers never exceed one retained file. Append, rotation, startup repair, reads, bundle preparation and deletion share one bounded queue. DEBUG is disabled by default and does not change the allowlist.

Startup removes extra numeric managed archive names, reduces oversized managed files to a complete line within the bound and removes incomplete final lines. Unrelated filenames are untouched. Regular-file, canonical-path, owner, device/inode and single-link checks refuse aliases and hardlinks before content access. The account owner receives mode 0700 for the directory and 0600 for files on POSIX. Windows uses an asynchronous fixed native PowerShell ACL operation with a path passed as environment data; it removes inherited and other explicit rules, grants only the current SID full control and verifies the resulting protected ACL. A missing/denied permission tool makes logging unavailable and latches the failure until explicit reinitialization. Closing the writer cancels its active permission helper and discards queued work. Account-equivalent hostile filesystem replacement and forensic erasure are outside the local-log guarantee.

`initializeLogs`, `append`, `read(slot, continuation)`, `deleteLogs(confirmed)`, `prepareBundle(selection, current)`, `catalog`, `status` and `close` are broker-internal interfaces. Deletion requires explicit confirmation, reports the number actually removed on partial failure and recreates the active file after successful cleanup.

## Settings log viewer

[STORY-004-019](epics/EPIC-004-onboarding/STORY-004-019-view-diagnostics.md) provides **Settings → Diagnostics**. Entering Diagnostics reads the active log with the most recently written records first. Choosing an archive loads its newest records. **Next page** replaces the displayed page with older records from the same file. **Refresh** reloads the newest records in the selected log. Displayed UTC times retain their recorded values even when clock adjustments make those values differ from write order. The selector labels the active log **Archive 1 (most recent)** and the four retained archive slots **Archive 2** through **Archive 5 (oldest)**, in rotation order. A slot with no managed file yields an empty first page.

The named read operation uses a trusted top-level desktop frame, the shared request budget and the writer's serialized queue. A successful page contains at most 64 scanned records, including invalid and unsupported records. Both sides validate closed wire shapes. The broker decodes each line against its schema version and catalog, then projects only UTC time, severity and controlled event name. It uses the recorded event time when present and the broker's recorded observation time otherwise. Invalid, oversized and unsupported lines contribute counts without contributing text. A file beyond the managed byte bound, busy queue or refused access produces a controlled result. The viewer receives no paths, raw lines, artifact metadata or correlation IDs.

A continuation contains a bounded byte offset and a broker-authenticated token bound to that offset, the managed slot and the file identity. The offset marks the end of the unread older records. The writer validates the token and line boundary inside the serialized read. Appends are visible on refresh and leave an existing continuation pointed at the same older records. Rotation, managed deletion, startup repair or writer replacement invalidates issued continuations. A missing file or a mismatch in device or inode makes its continuation stale. The broker keeps no cursor registry. On a stale result Settings discards the old page and offers **Refresh**. This keeps the read's coverage and uncertainty visible under PRIN-007 and PRIN-006.

Write, rotation, permission and deletion exceptions become controlled `unavailable` results. Capacity rejection is `busy`; invalid records, oversized records, missing confirmation and closed writers have separate statuses. Logging does not gate storage transactions or save acknowledgements. Failure never causes recursive logging or output of an exception. A subsequent admitted operation reconciles incomplete files before further append. Diagnostics are operational records rather than crash-durable research receipts; no file synchronization or physical power-loss guarantee is inferred from successful append.

## Delete retained logs

[STORY-004-020](epics/EPIC-004-onboarding/STORY-004-020-delete-diagnostics.md) adds **Delete logs** in **Settings → Diagnostics**. Each deletion requires its own explicit confirmation for the active and retained technical diagnostic files on this device. Confirmation initially focuses **Cancel**. While focus is in Diagnostics, **Escape** closes the confirmation and returns focus to **Delete logs**. The research store keeps its history, revisions, task and attempt records, and receipts (PRIN-013). The action covers the five managed slots. Saved bundles are user files that can be removed through the operating system. Deletion provides no forensic erasure guarantee.

The named operation validates an explicit confirmation at preload and broker admission. The broker uses the trusted top-level frame, shared request budget and the same writer queue as append, rotation and read. A successful result counts the files the writer actually removed. If deletion fails after removing one or more files, Settings shows an incomplete result and the actual count. The writer stops at the first filesystem failure. Later diagnostic events may appear in the active log. If deletion is refused or fails before removing any files, Settings reports that deletion is unavailable. A busy request reports its own result. A missing, invalid or late reply leaves the outcome uncertain (PRIN-006).

Settings refreshes the selected log through the separate read operation after deletion settles. The deletion result remains visible if that read fails or the researcher manually refreshes. A refresh reloads the current file state and never repeats a deletion. A new deletion requires a fresh confirmation.

## Save a reviewed diagnostic bundle

[STORY-004-021](epics/EPIC-004-onboarding/STORY-004-021-save-diagnostic-bundle.md) adds **Diagnostic bundle** in **Settings → Diagnostics**. Select one or more managed files and the inclusive UTC observation range. The initial selection contains all managed slots and the preceding 24 hours. **Preview bundle** scans these files in the writer's serialized queue, with the same admission and maximum of five files of 5 MiB each. A missing slot contains no records. The preview shows the full JSON text and counts invalid and unsupported lines in the selected files, including lines whose observation time cannot be validated (PRIN-007). If the encoded bundle exceeds 1 MiB (1,048,576 bytes), Settings shows the counts and asks for a narrower range. No partial bundle is prepared.

The UTF-8 JSON object contains `schema_version: 1`, `range` with canonical UTC `from` and `through` strings, and `records`. Records sort by `observed_timestamp` ascending. Equal timestamps retain ascending managed slot and then ascending byte-offset order. Slot and offset remain internal. Each record contains `observed_timestamp`, optional event `timestamp`, `severity_text`, `event_name`, and a `resource` object with `service.name` and `service.version`. The `attributes` object contains the catalog's `ohtia.component`, `ohtia.operation` and `ohtia.outcome`, with `ohtia.error.code` and `ohtia.duration_ms` when present. Only validated version-1 log records contribute fields. The export omits correlation and entity IDs, paths, raw lines, unsupported schemas, research content and provider content. The Settings viewer projects a smaller subset of the same diagnostic record catalog.

The broker keeps one prepared preview, scoped to its initiating window and trusted frame. Replacing the preview, cancelling it, changing the filter, leaving Diagnostics or disposing its window discards it. **Save diagnostic bundle** opens the native destination picker in the initiating window. The renderer supplies the broker-issued identifier for that exact preview. Cancelling the picker discards the preview. After the picker returns a destination, the broker checks that the preview is still current and writes its exact UTF-8 bytes, including any records since rotated out of the selected slots. The broker rechecks that approval is current just before atomically replacing the selected file from an exclusive, synced temporary file in the same directory. It refuses application data and configuration roots and protected profile fixtures. Failed or revoked writes preserve the previous destination and remove their temporary data when the filesystem permits. The temporary file permits access only to its owner on POSIX and starts with a protected current-account ACL on Windows, which the broker verifies before writing bytes. The saved file retains those permissions after the replacement. A forced process termination may leave a pending temporary file. A missing or invalid save reply or an unconfirmed cleanup produces controlled uncertainty (PRIN-006). Ohtia does not upload the file.
