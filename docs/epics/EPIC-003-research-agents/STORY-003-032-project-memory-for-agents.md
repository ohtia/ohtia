# STORY-003-032 — Project memory for agents

## Description

Add memory entries and versions, Virgilio's automatic `update_memory` in `direct_guidance` version 6, the reply's memory-change line with "Undo memory changes", memory in every agent input and the dependent-reply mark. STORY-003-033 adds the "Project memory" tab, the entry form, the researcher's own commands and the entry history.

## Acceptance criteria

- [ ] A goal or decision without a researcher source is rejected, a merge that includes one is rejected, and Virgilio cannot change an entry whose current version the researcher wrote, an undo's included.
- [ ] "Undo memory changes" restores the previous versions and announces "Memory changes undone.", and after a later version it changes nothing and shows "Ohtia can't undo these changes because an entry has changed since."
- [ ] The "Memory updated: {changes}" and "Memory not updated: {n} changes didn't fit Ohtia's rules." lines show their texts, with plural forms.
- [ ] Every agent receives the memory item in its exact layout, Josefa under version 4 and the synthesis under version 3, and setup receives none.
- [ ] The `update_memory` definition is sent exactly as in SPEC-003-037 with every version 6 request, beside a proposal tool or `propose_plan_change`; a reply with one proposal and one `update_memory` call is not `multiple_calls`, and a second `update_memory` call has every change rejected with `multiple_calls`.
- [ ] Message labels appear only on the researcher's and other agents' messages and resolve through the transfer manifest; each action writes the stated versions, a merge keeps its first entry and withdraws the others with `merged_into`, undoing an added entry withdraws it and undoing a merge makes every merged entry active again.
- [ ] Each rejection code is stored in the stated order and gives Virgilio's next input the note with its codes, and a stopped reply applies no change.
- [ ] The memory-change item sits at its task's reply position with rank 3, below the reply's text and its card, or alone when the reply saved no message, with revision 1 and revision 2 after an undo; a call with an empty `changes` array applies nothing and shows no item, and a reply with only that call and no text fails with `empty_reply`.
- [ ] `memory.undo` rejections return `memory_full` or `undo_unavailable` with their notices, saving nothing, and the 32 KiB limit is measured on the memory item with its labels.
- [ ] A reply with a plan of maximum size and three memory changes of 2,000 code points fits the 192 KiB output limit.
- [ ] STORY-003-031 is merged and its output is on the base branch: Attention-check reply measurements. Then `direct_guidance` version 6 applies the measurement rule to the replies STORY-003-031 recorded as well as to this story's.
- [ ] The limits hold and an overflowing change is rejected with the note to Virgilio.
- [ ] A reply based on an old version shows the mark (scenario 12) as its memory-review item of rank 4 and revision 1, announced through `research.subscribe`, while versions its own changes or their undo wrote never mark it; an entry edited from another conversation between a reply's dispatch and the saving of its message gives that reply the item in the transaction that saves the message.
- [ ] `docs/design-system.md` maps `notebook-pen` to memory changes.
- [ ] With the researcher's account, a decision told to Virgilio shows its "Memory updated" line, is used in another conversation, and Virgilio's later change of it marks the old reply.
