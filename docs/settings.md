# Settings and presentation preferences

## Ownership

Settings is a dialog with a page list and the selected page. Accessibility and appearance holds the Language, Appearance, Interface zoom, Characters, Workspace layout and Project memory text groups; Project memory text contains Source quote length (characters) and Entry text length (characters). AI services holds one group per connection, with its connection controls, the first-connection question, and its model list age and refresh action, followed by Simultaneous work with the AI replies at the same time control. The OpenRouter group also shows the key's expiry date when it has one, and below its row a line saying that OpenRouter's privacy settings, guardrails, plugins and observability destinations decide where messages go, with links to those OpenRouter settings and to its usage page. Agents holds the always-open default model and, under Each agent, one summary row per agent whose Change button shows its selects; a row stays open while it has an unresolved save notice, an unreadable model list or no usable model, and a notice that names an agent opens that row. [Research location](#research-location) provides the managed store inspection. Updates holds the Check for updates when Ohtia starts control of [SPEC-001-040](epics/EPIC-001-desktop-foundation/epic.md#spec-001-040-update-check-and-notice-in-the-application), enabled by default. Settings opens on Accessibility and appearance; a recovery action opens the page that owns its control. Below the 600 px compact width class the dialog shows either the page list or one page with Back; opening there starts at the list, and narrowing an open dialog keeps the page in use. A page list entry names a page whose rejected, uncertain, conflict, not-applied or read-failure notice is still shown. Changes save immediately; the dialog has a close action and no Save or Cancel action. The [Settings specification](epics/EPIC-002-basic-interface/epic.md#spec-002-010-extensible-settings-with-real-application-preferences) owns the product contract and the [save-state specification](epics/EPIC-002-basic-interface/epic.md#spec-002-025-settings-presentation-and-preference-save-states) owns the presentation treatments.

The renderer's [SettingsController](../packages/renderer/src/settings-controller.ts) owns appearance, character, zoom and project memory preference interaction state for one window. Keep it alive across dialog close/reopen so an unresolved write retains its identity. The existing [LanguageController](../packages/renderer/src/language-controller.ts) owns language. The originating [WorkspaceController](../packages/renderer/src/workspace-controller.ts) owns layout; Settings receives that controller and its state rather than loading a second layout record. [The installed composition](application-composition.md#installed-application) connects this authority to workspace chrome. Passive viewport changes, including zoom, do not save layout.

[SettingsDialog](../packages/renderer/src/settings-dialog.tsx) receives these controllers, translated content context and the actual platform. Its typed `SettingsSection` extension accepts a stable ID, localized heading, Lucide icon and delivered content, shown as another page. Add a page only with its real feature controls and operations. The foundation's [SettingsSurfaces](../packages/renderer/src/settings-surfaces.tsx) supplies the window lifetime and binds Settings, theme and zoom to the shared command registry. A workspace composition supplies the same originating layout authority to its other controls.

## Research location

Settings → Research location uses the [named location operation](application-port.md#envelopes-and-named-operations) when the page opens, when storage admission changes and when the researcher chooses **Check location**. It shows the admitted path or explains the reported reason it is unavailable.

The page explains that the folder contains private research and that its path may identify the account. Status updates retain keyboard focus. The startup recovery controls retain their own entry and authority. This presentation follows PRIN-006 and PRIN-011 in the [product definition](product-definition.md#product-principles).

## Named preference boundary

The [application port](application-port.md) retains exact-key runtime decoding, bounded messages, generation checks, transactional revisions and operation receipts. `presentation.read` and `presentation.subscribe` provide a generation-bound snapshot of the presentation records. Appearance continues to use `appearance.replace` and its receipt operation. `character.replace` and `character.receipt` own only `character_presentation`; `zoom.replace`, `zoom.adjust` and `zoom.receipt` own only `interface_zoom`. `sourceQuote.replace` and `sourceQuote.receipt` own only `project_memory_source_quote_length`. `entryText.replace` and `entryText.receipt` own only `project_memory_entry_text_length`. No operation accepts an arbitrary preference key, path or private buffer.

The [storage owner](../packages/utility/src/storage.ts) commits each character, zoom or project memory presentation preference and its receipt in one transaction. The immutable migrations that declare these preferences and receipts follow the existing [checkpoint and recovery procedure](storage.md). A duplicate operation returns its recorded result, while a different payload with the same identity conflicts. Terminal zoom endpoint refusals also retain a receipt, so a delayed duplicate cannot become a mutation after another window changes the scale. Replacing an invalid saved value requires an explicit valid command at its known revision; reads retain the rejected bytes.

The [trusted presentation broker](../packages/main/src/presentation-broker.ts) admits at most one unresolved zoom mutation application-wide. It converts a relative zoom intent using the latest confirmed percentage and revision, then sends the broker-only `zoom.commit` operation to the service. Renderer admission rejects that internal operation. A fresh relative acknowledgement must match the requested percentage and next revision. An older duplicate result must match the original durable receipt and never rewinds a newer confirmed factor. Endpoint refusals use the controlled `zoom_minimum`, `zoom_maximum` and `actual_size` outcomes, separately from a pending mutation’s `busy` result. A failed or uncertain mutation never previews a new factor. An uncertain operation retains its identity until its receipt resolves; a receipt absence in the same service generation does not release admission. The broker can query its retained original identity during service initialization, a window’s rendering application or a later blocked intent, so closing the originating view cannot strand the global lock.

Main owns the effective appearance source through the native theme, background and overlay, so new and recovering windows share the same CSS media preference before display; renderer Settings retains draft and receipt state without a competing document theme override. Main applies confirmed zoom through the owned renderer's zoom factor and verifies the reported factor. `zoom.apply` retries rendering and reports the applied percentage and revision without writing a preference. Its result is separate from the durable receipt. Language, appearance, characters, zoom and both project memory presentation preferences publish across windows; each existing window retains its own layout. These boundaries preserve uncertainty and coverage under PRIN-006, PRIN-007 and PRIN-016, and grant no inference, external-transfer or human-confirmation authority.

## Project memory text lengths

Source quote length and entry text length are independent preferences shared by every project in the desktop profile. Missing values default to 144 and 288 characters respectively. Each field accepts whole numbers from 0 to 9,007,199,254,740,991 and saves on blur or Enter. Zero shows the complete text for that field. Invalid input leaves the confirmed value in effect. Standard Settings save notices and receipts handle rejected or uncertain writes. The [Project memory view](epics/EPIC-003-research-agents/epic.md#spec-003-038-project-memory-view-and-entries) defines how each text is displayed.

## Inference concurrency

The window-owned [LimitsController](../packages/renderer/src/limits-controller.ts) keeps the saved record and original operation identity across dialog closure. [The number field](../packages/renderer/src/limits-panel.tsx) accepts whole numbers from 1 to 50 on blur or Enter, preserving IME composition and exposing the range notice through its accessible description. Each connected service has the help variant for its connection kind, and a declared lower connection cap stays visible without overriding that cap. Running-reply help uses the saved limit and the current count, including the special one-reply case.

`limits.read`, `limits.replace` and `limits.receipt` use the existing named preference boundary. The last accepted write wins across windows, advances the execution-limit revision once and atomically records `operation_id`, `value` and `result_revision` in `execution_limits_receipts`. Replays and recorded receipts return that historical value and revision with the current running count; rejected values have no receipt. Local-processing policy stays unchanged. The service serializes replacement with task admission: lowering leaves running replies alone, and raising pumps only eligible queued work, preserving plan pauses, restart pauses and uncertain outcomes under [ADR-0051](adr/adr-0051-research-agent-task-execution.md#scheduling-and-required-limits).

Settings observes the window’s single `research.subscribe` stream, including windows with no project. Limit changes and inference-activity notices trigger a reread; a sequence gap also rereads and recovers through the existing conversation subscription owner. The controller ignores older preference revisions while refreshing the live running count, and compares revisions only within their admitted service generation. Failure and uncertainty use the existing Settings messages; recovery actions sit outside notice boxes. These controls preserve explicit researcher choice and uncertainty (PRIN-001, PRIN-006 and PRIN-016).

## Update check on startup

The startup update check of [SPEC-001-040](epics/EPIC-001-desktop-foundation/epic.md#spec-001-040-update-check-and-notice-in-the-application) is a boolean preference in `update_check`, enabled when no record exists. `updateCheck.read`, `updateCheck.replace` and `updateCheck.receipt` use the named preference boundary with expected revisions and `update_check_receipts`; there is no first-run notice. An unreadable saved value reads as disabled until an explicit replacement. Main reads the preference whenever storage opens; the first successful read decides the startup check, which runs at most once per launch. When it is enabled, the [update broker](../packages/main/src/update-broker.ts) asks GitHub's latest-release endpoint once through the [bounded request](../packages/main/src/update-check.ts); the manual `update.check` works whatever the preference says. The request is a GET with only `Accept` and `User-Agent: Ohtia` headers, follows no redirect or proxy, and is bounded by `update_check_ms` and `update_check_response_bytes`. A failed startup check stays silent; a failed manual check reports its controlled failure. Only an installed build with a final version checks. A newer version exists only when the release is final and greater than the running version under SemVer precedence.

## Rendering and interaction

The native modal primitive provides inert background, focus containment, Escape handling and trigger restoration. Language uses the shared 25-entry autonym table. Appearance uses native radios and decorative fixed-reference workspace miniatures; System observes the operating-system color preference. Characters uses native radios and a static 96 CSS px preview, with the compact glasses symbol in Hidden mode. System reduced motion takes precedence over Animated without changing its saved value.

Save states use text and icons beside group headings or in durable inline notices. A confirmed receipt survives a subsequent read/application failure. Check queries the original uncertain operation; Try again creates a new explicit intent after a definitive failure. Apply again retries only rendering. Passive snapshots do not announce another save, older revisions do not replace newer records, and disposed controllers ignore late responses. A locale or appearance update does not remount private input or translate research content.

## Recovery and command feedback

Command outcomes and their command IDs publish through the window-owned registry result subscription once per admitted intent. Unavailable reasons are discarded when current registry availability no longer supports them; a refusal by another window is described as the last action’s result, not proof that a save is still pending. Limit and busy reasons appear in the active dialog or the window when no dialog is open. Preference failures, unresolved receipts and display failures retain the same controlled actions outside Settings; opening the dialog keeps the feature controller and original operation identity. Recovery actions preserve a stable control or Settings entry as their focus target; opening from a window notice retains that trigger across the modal lifetime and uses the stable Settings entry if the original notice has resolved.

A missing receipt in the current service generation does not prove that its command has ceased. Keep zoom admission blocked, use Check to query the original receipt, and do not repeat the mutation. If the service remains healthy and no terminal receipt becomes available, end the application session through its normal quit procedure and resume only after confirmed service cessation and a fresh admitted generation; then inspect the current preference and original durable receipt before making a new explicit choice. If cessation remains unknown, keep the mutation unsubmitted. Service recovery likewise starts a new generation only after the old child has ceased. This conservative rule follows the [presentation receipt contract](epics/EPIC-002-basic-interface/epic.md#spec-002-021-presentation-receipts-and-deterministic-event-ordering).

Invalid stored values remain available for inspection until an explicit valid replacement is accepted at their known revision. Selecting a different valid value can replace them; the fallback itself is not silently persisted. The named replacement operation also accepts a deliberate replacement with the displayed fallback value. Reads and reopening Settings never perform that replacement.
