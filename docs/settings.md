# Settings and presentation preferences

## Ownership

Settings groups Language, Appearance and Workspace layout in one Accessibility and appearance section. Appearance contains the interface zoom and character controls. Changes save immediately; the dialog has a close action and no Save or Cancel action. The [Settings specification](epics/EPIC-002-basic-interface/epic.md#spec-002-010-extensible-settings-with-real-application-preferences) owns the product contract and the [save-state specification](epics/EPIC-002-basic-interface/epic.md#spec-002-025-settings-presentation-and-preference-save-states) owns the presentation treatments.

The renderer's [SettingsController](../packages/renderer/src/settings-controller.ts) owns appearance, character and zoom interaction state for one window. Keep it alive across dialog close/reopen so an unresolved write retains its identity. The existing [LanguageController](../packages/renderer/src/language-controller.ts) owns language. The originating [WorkspaceController](../packages/renderer/src/workspace-controller.ts) owns layout; Settings receives that controller and its state rather than loading a second layout record. Passive viewport changes, including zoom, do not save layout.

[SettingsDialog](../packages/renderer/src/settings-dialog.tsx) receives these controllers, translated content context and the actual platform. Its typed `SettingsSection` extension accepts a stable ID, localized heading and delivered content. Add a section only with its real feature controls and operations. The foundation's [SettingsSurfaces](../packages/renderer/src/settings-surfaces.tsx) supplies the window lifetime and binds Settings, theme and zoom to the shared command registry. A workspace composition supplies the same originating layout authority to its other controls.

## Named preference boundary

The [application port](application-port.md) retains exact-key runtime decoding, bounded messages, generation checks, transactional revisions and operation receipts. `presentation.read` and `presentation.subscribe` provide a generation-bound snapshot of the three presentation records. Appearance continues to use `appearance.replace` and its receipt operation. `character.replace` and `character.receipt` own only `character_presentation`; `zoom.replace`, `zoom.adjust` and `zoom.receipt` own only `interface_zoom`. No operation accepts an arbitrary preference key, path or private buffer.

The [storage owner](../packages/utility/src/storage.ts) commits each character or zoom preference and its receipt in one transaction. The immutable presentation-receipt migration follows the existing [checkpoint and recovery procedure](storage.md). A duplicate operation returns its recorded result, while a different payload with the same identity conflicts. Terminal zoom endpoint refusals also retain a receipt, so a delayed duplicate cannot become a mutation after another window changes the scale. Replacing an invalid saved value requires an explicit valid command at its known revision; reads retain the rejected bytes.

The [trusted presentation broker](../packages/main/src/presentation-broker.ts) admits at most one unresolved zoom mutation application-wide. It converts a relative zoom intent using the latest confirmed percentage and revision, then sends the broker-only `zoom.commit` operation to the service. Renderer admission rejects that internal operation. A fresh relative acknowledgement must match the requested percentage and next revision. An older duplicate result must match the original durable receipt and never rewinds a newer confirmed factor. Endpoint refusals use the controlled `zoom_minimum`, `zoom_maximum` and `actual_size` outcomes, separately from a pending mutation’s `busy` result. A failed or uncertain mutation never previews a new factor. An uncertain operation retains its identity until its receipt resolves; a receipt absence in the same service generation does not release admission. The broker can query its retained original identity during service initialization, a window’s rendering application or a later blocked intent, so closing the originating view cannot strand the global lock.

Main applies confirmed zoom through the owned renderer's zoom factor and verifies the reported factor. `zoom.apply` retries rendering and reports the applied percentage and revision without writing a preference. Its result is separate from the durable receipt. Language, appearance, characters and zoom publish across windows; each existing window retains its own layout. These boundaries preserve uncertainty and coverage under PRIN-006, PRIN-007 and PRIN-016, and grant no inference, external-transfer or human-confirmation authority.

## Rendering and interaction

The native modal primitive provides inert background, focus containment, Escape handling and trigger restoration. Language uses the shared 25-entry autonym table. Appearance uses native radios and decorative fixed-reference workspace miniatures; System observes the operating-system color preference. Characters uses native radios and a static 96 CSS px preview, with the compact glasses symbol in Hidden mode. System reduced motion takes precedence over Animated without changing its saved value.

Save states use text and icons beside group headings or in durable inline notices. A confirmed receipt survives a subsequent read/application failure. Check queries the original uncertain operation; Try again creates a new explicit intent after a definitive failure. Apply again retries only rendering. Passive snapshots do not announce another save, older revisions do not replace newer records, and disposed controllers ignore late responses. A locale or appearance update does not remount private input or translate research content.

## Recovery and command feedback

Command outcomes and their command IDs publish through the window-owned registry result subscription once per admitted intent. Unavailable reasons are discarded when current registry availability no longer supports them; a refusal by another window is described as the last action’s result, not proof that a save is still pending. Limit and busy reasons appear in the active dialog or the window when no dialog is open. Preference failures, unresolved receipts and display failures retain the same controlled actions outside Settings; opening the dialog keeps the feature controller and original operation identity. Recovery actions preserve a stable control or Settings entry as their focus target; opening from a window notice retains that trigger across the modal lifetime and uses the stable Settings entry if the original notice has resolved.

A missing receipt in the current service generation does not prove that its command has ceased. Keep zoom admission blocked, use Check to query the original receipt, and do not repeat the mutation. If the service remains healthy and no terminal receipt becomes available, end the application session through its normal quit procedure and resume only after confirmed service cessation and a fresh admitted generation; then inspect the current preference and original durable receipt before making a new explicit choice. If cessation remains unknown, keep the mutation unsubmitted. Service recovery likewise starts a new generation only after the old child has ceased. This conservative rule follows the [presentation receipt contract](epics/EPIC-002-basic-interface/epic.md#spec-002-021-presentation-receipts-and-deterministic-event-ordering).

Invalid stored values remain available for inspection until an explicit valid replacement is accepted at their known revision. Selecting a different valid value can replace them; the fallback itself is not silently persisted. The named replacement operation also accepts a deliberate replacement with the displayed fallback value. Reads and reopening Settings never perform that replacement.
